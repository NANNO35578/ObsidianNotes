## 其实是CORS问题
这是典型的跨域问题：浏览器从 `http://localhost:5173` 直接访问 WSL 内的 `http://localhost:8888`，后端未返回 `Access-Control-Allow-Origin`，预检被拦截。你有两种解法，任选其一：

## 方案 A：前端走代理（推荐，避免改后端）
1) 把 `src/utils/request.js` 的 `baseURL` 改回代理写法：
```js
const baseURL = import.meta.env.DEV ? '/api' : 'http://localhost:8888'
```
2) 保持 `vite.config.js` 的代理配置：
```js
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:8888',
      changeOrigin: true,
      secure: false,
    }
  }
}
```
3) 重启前端 dev 服务器 (`npm run dev`)。  
这样浏览器请求是同源的 `/api/...`，由 Vite 转发到 8888，不再触发浏览器 CORS 校验。

## 方案 B：改后端开启 CORS
如果不想用代理，就在后端加 CORS 响应头，至少：
- `Access-Control-Allow-Origin: http://localhost:5173`（或 `*`，如需携带 Cookie/凭证则不能用 `*`）
- `Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS`
- `Access-Control-Allow-Headers: Content-Type, Authorization`
- 处理预检 `OPTIONS` 直接 204/200 返回上述头。

若你用的是 JWT 放在 header（非 Cookie），设置上述即可；如果用 Cookie/Session，再加：
- `Access-Control-Allow-Credentials: true`
并且前端 axios 要设置 `withCredentials: true`。

## 补充
- 从 Windows 浏览器访问 WSL 服务是可以的，Postman 能通说明端口已透出，问题只在浏览器 CORS 校验。  
- 选方案 A 最快，不用改后端；选方案 B 需改后端。  
- 改完记得重启对应服务，再在浏览器控制台 Network 看预检响应是否带上允许的 CORS 头。
