# 数据库介绍

## 什么是数据库

数据库是"按照数据结构来组织、存储和管理数据的仓库"，是一个长期存储在计算机内的、有组织的、可共享的、统一管理的大量数据的集合。

- **查找更快**：通过索引等机制实现高效数据检索
- **数据共享**：多个用户/应用可同时访问
- **数据独立性**：数据与应用程序解耦

## 数据库的由来

- 规范化的本地存储
- 加密与安全控制
- 多用户共享与并发控制

## 数据库的分类

### 关系型数据库

采用二维表结构存储数据，典型代表：MySQL、Oracle、SQL Server、PostgreSQL。

| name | age |
|------|-----|
| zhangsan | 18 |
| xiaoming | 18 |

### 非关系型数据库（NoSQL）

也叫 NoSQL，通常采用 key-value 等非二维表结构，典型代表：Redis、MongoDB、Cassandra。

| key | value |
|-----|-------|
| "id=0" | zhangsan |
| "id=1" | name=zhangsan, age=12 |
| "id=2" | name=lucy, age=16 |

# 数据库范式

> 什么是范式？要想设计一个好的关系，必须使关系满足一定的约束条件，此约束已经形成了规范。按照规范设计可以使结构简洁明晰，不会因为插入、删除、更新数据导致异常。

**常见名词**：

| 名词 | 说明 |
|------|------|
| 属性 | 特征，表中的一列（字段），如 A |
| 元组 | 表中的一行（记录） |
| 码 | 能唯一确定表中一行的属性，码不止一个时称为候选码 |
| 主码（主键） | 从候选码中挑选一个主要确定这一行的属性 |
| 主属性 | 在任何一个候选码中出现过的属性 |
| 非主属性 | 没有出现在任何一个候选码中的属性 |

## 第一范式（1NF）——属性不可分

属性不可分：每个字段都是原子的，不可再分。

**符合 1NF**：

| name | tel | sex |
|------|-----|-----|
| 小明 | 19198986565 | male |
| 小红 | 13878789595 | female |

**不符合 1NF（属性可分）**：

| name | contact |
|------|---------|
| 小明 | tel:19198986565, email:xm@test.com |
| 小红 | tel:13878789595, email:xh@test.com |

> `contact` 字段可拆分为 `tel` 和 `email`，不符合 1NF。

## 第二范式（2NF）——消除部分依赖

> 在 1NF 基础上，不存在组合关键字中的某些字段决定非关键字段（组合关键字不可拆），即**非关键字字段全部由组合关键字整体决定**，消除非主属性对码的部分函数依赖。

**不符合 2NF 的例子**：

选课课表 `SelectCourse(学号, 姓名, 年龄, 课程名称, 成绩, 学分)`

- 主键为（学号, 课程名称）组合
- 但 `姓名`、`年龄` 只依赖于 `学号`（部分依赖）
- `学分` 只依赖于 `课程名称`（部分依赖）

**问题**：
1. 数据冗余：同一学生姓名重复出现，同一课程学分重复出现
2. 更新异常：修改学生姓名需更新所有相关记录
3. 插入异常：未选课的学生无法插入，无学生选的课程无法插入

**解决**：拆表

| 表名 | 字段 |
|------|------|
| 学生 | 学号, 姓名, 年龄 |
| 课程 | 课程名称, 学分 |
| 选课 | 学号, 课程名称, 成绩 |

## 第三范式（3NF）——消除传递依赖

> 在 2NF 基础上，不存在非主属性对码的传递依赖。
> 传递依赖：关键字段 → 非关键字段1 → 非关键字段2

**不符合 3NF 的例子**：

学生关系表：`(学号, 姓名, 年龄, 所在学院, 学院地点, 学院电话)`

- `学号` → `所在学院` → `学院地点`、`学院电话`（传递依赖）

**解决**：拆表

| 表名 | 字段 |
|------|------|
| 学生 | 学号, 姓名, 年龄, 所在学院 |
| 学院 | 学院名称, 学院地点, 学院电话 |

## BCNF（鲍依斯-科得范式）

> 在 3NF 基础上，不存在主属性对码的部分依赖和传递依赖，即**不存在关键字段决定关键字段**的情况。

**不符合 BCNF 的例子**：

仓库管理系统：`(仓库ID, 存储物品ID, 管理员ID, 数量)`

- 假设一个管理员只管理一个仓库，一个仓库有多个管理员
- 候选码：（仓库ID, 存储物品ID）和（管理员ID, 存储物品ID）
- `管理员ID` → `仓库ID`（主属性之间的依赖）

**解决**：拆表

| 表名 | 字段 |
|------|------|
| 仓库管理 | 仓库ID, 管理员ID |
| 仓库库存 | 仓库ID, 存储物品ID, 数量 |

# 存储过程

> 存储过程（Stored Procedure）是一组为了完成特定功能的 SQL 语句集合，经编译后存储在数据库中，用户通过指定存储过程的名字并给出参数来执行它。

**特点**：
- 预编译，执行效率高
- 减少网络传输（只需传过程名和参数）
- 可重复使用
- 支持参数传递和返回值

**基本语法（MySQL）**：

```sql
DELIMITER //
CREATE PROCEDURE procedure_name(IN param1 INT, OUT param2 VARCHAR(50))
BEGIN
    -- SQL 语句
    SELECT column_name INTO param2 FROM table_name WHERE id = param1;
END //
DELIMITER ;

-- 调用
CALL procedure_name(1, @result);
SELECT @result;
```

# 触发器

> 触发器（Trigger）是一种特殊的存储过程，它在特定的表上发生 INSERT、UPDATE、DELETE 事件时自动触发执行。

**特点**：
- 自动执行，无需手动调用
- 与表绑定，表删除则触发器删除
- 可用于数据完整性约束、审计日志、级联操作等

**基本语法（MySQL）**：

```sql
DELIMITER //
CREATE TRIGGER trigger_name
    BEFORE/AFTER INSERT/UPDATE/DELETE
    ON table_name
    FOR EACH ROW
BEGIN
    -- 触发时执行的 SQL 语句
    -- 使用 NEW 引用新行，OLD 引用旧行
END //
DELIMITER ;
```

# 事务

> 事务（Transaction）是一组要么全部成功、要么全部失败的 SQL 操作序列，是数据库并发控制和恢复的基本单位。

## ACID 特性

| 特性 | 全称 | 说明 |
|------|------|------|
| A | 原子性（Atomicity） | 事务中的操作要么全部执行，要么全部不执行 |
| C | 一致性（Consistency） | 事务执行前后，数据库从一个一致性状态转换到另一个一致性状态 |
| I | 隔离性（Isolation） | 并发事务之间互不干扰，一个事务的中间状态对其他事务不可见 |
| D | 持久性（Durability） | 事务一旦提交，其修改永久保存在数据库中，即使系统故障也不会丢失 |

## 事务的基本操作

```sql
-- 开启事务
START TRANSACTION;  -- 或 BEGIN

-- 执行 SQL 操作
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

-- 提交事务（成功）
COMMIT;

-- 回滚事务（失败）
-- ROLLBACK;
```

## 并发问题与隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 避免 | 可能 | 可能 |
| 可重复读（Repeatable Read） | 避免 | 避免 | 可能（MySQL InnoDB 通过 MVCC 避免） |
| 串行化（Serializable） | 避免 | 避免 | 避免 |
