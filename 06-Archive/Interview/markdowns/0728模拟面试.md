> [!abstract] 类与类之间的关系及其详解?
> *横向*:
> - **组合 (Composition)** : 组合表示强拥有关系，一个类包含另一个类的对象，且被包含对象的生命周期由包含类管理。当包含类对象销毁时，被包含的对象也会被销毁
> - **依赖 (Dependency)** : 依赖表示一个类在某一时刻使用另一个类，通常出现在方法参数、返回值类型或局部变量中。被依赖类的生命周期不受依赖类影响，依赖关系一般是临时性的
> - **关联 (Association)** : 关联表示类之间的交互关系，通常通过指针或引用传递。类之间的生命周期独立，关联的对象不由当前类管理，通常表现为对象间的弱关系
> - **聚合 (Aggregation)** : 聚合是一种“整体-部分”关系，其中部分对象可以独立于整体存在。与组合不同，聚合关系中的部分对象的生命周期不依赖于整体类，它们可以在多个类中共享
> 
> *纵向*: 
> - **继承 (Inheritance)** : 继承是一种“是一个”的关系，表示子类继承父类的属性和方法，从而实现代码复用。子类可以扩展或修改父类的行为，继承支持单继承和多继承，并能实现多态
> - **多态 (Polymorphism)** : 多态允许通过父类指针或引用调用子类重写的方法，使得同一接口可以表现出不同的行为，增强了程序的灵活性和可扩展性。它通常通过虚函数和方法重写实现




> [!abstract] 七个设计原则?
> - ==单一职责原则（SRP）== ：一个类应该只有一个引起它变化的原因. 降低类的复杂度，提高类的可读性和可维护性，降低变更引起的风险
> - ==开闭原则（OCP）== ：软件实体（类、模块、函数等）应该对扩展开放，对修改关闭。使软件系统更易于维护和扩展，在不修改现有代码的基础上添加新功能
> - ==里氏替换原则（LSP）== ：子类可以替换其父类并且出现在父类能够出现的任何地方，而不会影响系统的正确性。保证父类的复用性和子类的可扩展性，增强系统的健壮性
> - ==接口隔离原则（ISP）== ：客户端不应该依赖它不需要的接口，一个类对另一个类的依赖应该建立在最小的接口上。避免接口的臃肿，提高接口的内聚性，使系统更加灵活和可维护
> - ==依赖倒置原则（DIP）== ：高层模块不应该依赖低层模块，两者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。降低模块间的耦合度，提高系统的可维护性和可扩展性，使代码更具灵活性
> - ==迪米特法则（LoD）== ：一个对象应该对其他对象有最少的了解，即一个类应该尽量减少与其他类的交互。降低类之间的耦合度，使系统的各个模块相对独立，提高系统的可维护性和可扩展性
> - ==合成复用原则（CRP）== ：尽量使用对象组合/聚合，而不是继承来达到复用的目的。降低类之间的耦合度，使系统更加灵活，提高代码的复用性


> [!abstract] 单例模式中懒汉式如何解决资源竞争问题?
1. 双检锁
```cpp
static Singleton& getInstance() {
  if (instance == nullptr) {                // 第一次检查. 无锁，非原子操作
    std::lock_guard<std::mutex> lock(mtx);  // 加锁

    if (instance == nullptr) {     // 第二次检查. 加锁后，但无内存序保护
      instance = new Singleton();  // 构造实例
    }
  }
  return *tmp;
}
```
- 多线程不安全
2. 双重检查锁(DCLP，Double-Checked Locking)
```cpp
#include <atomic>
#include <iostream>
#include <mutex>
class Singleton {
public:
  static Singleton& getInstance() {
    Singleton* tmp = instance.load(std::memory_order_acquire);  // 第一次检查（无锁）
    if (tmp == nullptr) {
      std::lock_guard<std::mutex> lock(mtx);  // 加锁
      tmp = instance.load(std::memory_order_relaxed);

      if (tmp == nullptr) {
        tmp = new Singleton();                           // 构造实例
        instance.store(tmp, std::memory_order_release);  // 存储结果
      }
    }
    return *tmp;
  }

private:
  Singleton(const Singleton&) = delete;
  Singleton& operator = (const Singleton&) = delete;
  Singleton() {
    std::cout << "Singleton (双检锁) 构造完成\n";
  }
  static std::atomic<Singleton*> instance;  // 原子指针
  static std::mutex              mtx;       // 互斥锁
};
// 初始化静态成员
std::atomic<Singleton*> Singleton::instance{nullptr};
std::mutex              Singleton::mtx;
```
- 如何真正解决指令重排问题：将操作变成原子操作，也就是new内部的三个指令，确保一次性完成, 把构造过程封装成函数，通过call_once调用函数. call_once保证函数代码只执行一次，内部实现了多线程安全
```cpp
#include <iostream>
#include <mutex>

class Singleton {
public:
  static Singleton& getInstance() {
    std::call_once(flag, []() { /* 保证初始化代码仅执行一次 */ instance = new Singleton(); });
    return *instance;
  }
  Singleton(const Singleton&) = delete;
  Singleton& operator = (const Singleton&) = delete;
private:
  Singleton() {
    std::cout << "Singleton (call_once) 构造完成\n ";
  }
  static Singleton*     instance;  // 静态指针
  static std::once_flag flag;      // 一次性标志
};
// 初始化静态成员
Singleton*     Singleton::instance = nullptr;
std::once_flag Singleton::flag;
```


> [!abstract] 常引用和右值引用的联系与差异?

## 对称加密与非对称加密的区别？为何 HTTPS 混合使用两种加密方式？

### 对称加密：
- **定义**：加密和解密使用相同的密钥。
- **特点**：
  - **速度快**：算法简单，运算效率高，适合加密大量数据。
  - **密钥管理问题**：密钥必须安全传输，否则可能会被截获。
  - **使用场景**：适合加密数据传输，如文件加密、磁盘加密等。
  - **不适合公开网络**：因为密钥一旦被窃取，加密内容就不再安全。

### 非对称加密：
- **定义**：加密和解密使用不同的密钥，通常由公钥和私钥组成。
- **特点**：
  - **公钥加密**，**私钥解密**：可以公开公钥，私钥只有接收者持有。
  - **计算量大**：基于复杂的数学问题（如离散对数、椭圆曲线算法），因此比对称加密慢。
  - **使用场景**：适用于小数据量加密，如数字证书、密钥交换、身份验证等。
  - **密钥交换**：公钥用于加密，私钥用于解密，确保数据安全。
  
### 为什么 HTTPS 混合使用两种加密方式？
- HTTPS协议结合了对称加密和非对称加密的优点。**非对称加密**用来安全地交换对称加密的密钥（会话密钥），保证密钥在传输过程中的安全。**对称加密**用来加密会话中的实际数据，速度较快，适合大规模数据传输。
  
  具体流程：
  1. 客户端和服务器通过非对称加密（如RSA或ECDHE）交换密钥。
  2. 一旦会话密钥（对称密钥）安全地交换完成，之后的数据传输则使用对称加密（如AES）进行加密。
  
  这样能在保证安全性的同时，提高数据传输的效率。

## 对称加密为什么比非对称加密快，非对称加密为什么比对称加密安全?

### 为什么对称加密比非对称加密快？
1. **计算简单**：对称加密使用的加密算法（如AES、DES）基于简单的数学运算，例如位运算（异或）、代换和置换操作，运算量小
2. **优化**：对称加密可以进行更高效的硬件加速（如GPU或专用加密芯片），在处理大量数据时具有更高的吞吐量
   反之，非对称加密算法，如RSA和椭圆曲线加密（ECDSA、ECDHE），使用的是更复杂的数学运算（如模幂运算、椭圆曲线离散对数），计算量大，速度较慢

### 为什么非对称加密比对称加密安全？
1. **密钥对不同**：非对称加密基于数学难题（如椭圆曲线离散对数问题或RSA的因式分解问题），即使攻击者知道公钥，也无法推导出私钥。
   - **对称加密的风险**：在对称加密中，密钥需要在双方之间安全共享，一旦密钥被截获，数据就不再安全。
   
2. **数字签名和身份认证**：
   - **数字签名**：非对称加密可以通过私钥对数据进行签名，其他人可以用公钥验证签名，从而确认数据的来源。
   - **身份认证**：证书和公钥基础设施（PKI）使用非对称加密来验证身份，防止身份伪造。
   
3. **难以破解**：非对称加密的安全性依赖于现代计算无法有效解决的数学问题（如大数因式分解、椭圆曲线离散对数等），其强度随着密钥长度的增加而显著增强。

# 在虚拟内存中, 两个进程能有相同地址吗? 
[In virtual memory, can two different processes have the same address?](https://stackoverflow.com/questions/3552633/in-virtual-memory-can-two-different-processes-have-the-same-address)

> 在虚拟内存中, 两个不同进程能拥有相同地址吗?
> 若不能, 怎么解释有些进程能够访问另一个进程的内存的? 比如调试的时候, 调试器能访问并修改变量的值吗


- 两个不同进程可以有相同的虚拟内存地址. 因为在32位机器上, 每个进程有自己的页表, 每个进程认为自己有自己的虚拟4G内存. 所以进程1和进程2都可以访问`0xabcdef`, 当实际的物理内存可能会不一样
- 调试器是相同的原理, 两个进程可以同时访问相同的地址, 因此它可以动态修改变量等

1. 理论上，在任何当前流行的操作系统（Win、Linux、Unix、Sol 等）中，用户执行的每个进程最初都允许使用 4GB 的地址范围（32 位平台上为 0x00000000 到 0xffffffff），无论是简单的 Hello World 程序，还是托管 StackOverflow 站点的复杂 Web 容器。这意味着每个进程的范围都虚拟地从相同的起始地址开始，并以相同的地址空间结束。因此，显然每个进程在其各自的虚拟地址空间范围内都有相同的虚拟地址。因此，对于你的第一个问题，答案是肯定的
2. 操作系统执行任何进程时都会有所不同。现代操作系统是多任务操作系统，它们在任何时间点都会运行多个进程。因此，在主内存中容纳每个进程的 4GB 内存根本不可行。因此，操作系统使用分页系统，将虚拟地址范围（0x00000000 到 0xffffffff）划分为 4KB 大小的页面（并非总是如此）。因此，在启动进程之前，它实际上会将初始所需的页面加载到主内存中，然后根据需要加载其他虚拟页面范围。因此，将虚拟内存加载到物理内存（主内存）称为内存映射。在此过程中，您根据主存储器中的可用插槽将页面的虚拟地址范围映射到物理地址范围（如 ox00000000 到 ox00001000 虚拟地址范围到 0x00300000 到 0x00301000 物理地址范围）。因此，在任何时间点，只有一个虚拟地址范围将映射到该特定的物理地址范围，因此第二个问题的答案是否定的
3. **但是** 共享内存的概念是一个例外，所有进程可以共享部分虚拟地址范围，这些虚拟地址将被映射到一个公共的物理地址空间。所以在这种情况下，答案可能是肯定的
4. 举例来说，在 Linux 上，每个可执行文件都需要 libc.so 库来执行程序可执行文件。每个进程都会加载它们所需的库，并在它们的地址空间中为它们分配一些虚拟地址页面范围。现在考虑这样一种情况：你正在执行 100 个进程，每个进程都需要这个库 libc.so。因此，如果操作系统在每个进程中都为这个库 libc.so 分配虚拟地址空间，那么你可以想象库 libc.so 的重复程度，并且很有可能在任何时间点你都会在主存中获得多个 libc.so 地址范围页面的实例。因此，为了实现冗余，操作系统会将 libc.so 加载到每个进程的特定虚拟地址空间范围，该范围映射到主存中的固定物理地址范围。因此，每个进程都将引用该固定物理地址范围来执行 libc.so 中的任何代码。因此，在这种情况下，每个进程也共享一些物理地址范围
5. 但是在用户 malloced 的虚拟地址范围映射中，两个进程不可能同时具有相同的物理地址

> [!abstract] 对于调试器访问程序数据
> 我认为调试器不会直接访问被调试的其他进程，而是与被调试进程中的运行时进行通信以进行更改。 
> 也就是说，如果您有权限，操作系统或处理器指令也许可以提供对其他进程内存的访问/修改。
> 这并不意味着它拥有相同的地址，只是说进程 1 可以“访问进程 2 中 @address1 的内存”。某个进程（处理器/操作系统/运行时）会为进程 1 执行此操作。
