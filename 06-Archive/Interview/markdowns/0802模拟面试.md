  `[!!abstract: 静态库和动态库的性质与关联?]`
## 1. **静态库与动态库的区别**
> * **静态库（Static Library）**：
> > * 文件扩展名：Linux / MacOS 为 `.a`，Windows 为 `.lib`。
> > * 在编译时，库文件被嵌入到最终的可执行文件中。
> > * 静态链接：程序启动时不需要依赖外部的动态库，所有的代码和资源在链接阶段就已经融合。
> > * 优点：部署时不需要额外的库文件，启动速度较快。
> > * 缺点：程序体积较大，更新库文件需要重新编译所有依赖该库的程序。
>
> * **动态库（Dynamic Library）**：
> > * 文件扩展名：Linux / MacOS 为 `.so`，Windows 为 `.dll`。
> > * 在运行时加载，代码不直接嵌入到可执行文件中。
> > * 动态链接：程序启动时需要加载外部动态库，程序和库文件可以独立更新。
> > * 优点：程序体积较小，库文件可以共享给多个程序。
> > * 缺点：运行时依赖库的存在，库文件若缺失或版本不匹配可能导致程序崩溃。

#####  2. **Linux / MacOS / Windows 中静态库和动态库的使用与调用**

* **Linux / MacOS**：
  * *静态库*：使用 `.a` 文件. 在编译时通过 `-l<library_name>` 来链接
  * 例如链接到名为 `libfoo.a` 的静态库：`{bash}g++ -o main main.cpp -lfoo`

  * *动态库*：使用 `.so` 文件. 在运行时，程序需要通过 `LD_LIBRARY_PATH` 环境变量来查找动态库，或者通过 `-rpath` 参数指定库的路径
  * 例如链接到名为 `libfoo.so` 的动态库：`{bash}g++ -o main main.cpp -lfoo -L/path/to/libs`


* **Windows**：
  * 静态库：使用 `.lib` 文件，在编译时直接链接：```{bash}cl main.cpp /link foo.lib```
  * 动态库：使用 `.dll` 文件，链接时需要依赖相应的 `.lib` 文件（`import.lib`）
  * 在编译时链接 `.lib`，而在运行时加载 `.dll`：`{bash}cl main.cpp foo.lib`. 在运行时，需要保证程序能够找到对应的 `.dll` 文件（通常通过 `PATH` 环境变量）
  * **Msys / MinGW**：为了处理不同平台间的差异，可能使用 `.dll.a` 扩展名作为 `import.lib`，使得编译器能够理解并正确链接：`{bash}gcc -o main main.c -lfoo`. 这里 `libfoo.dll.a` 是静态链接 `dll` 的导入库，链接后程序会动态加载 `foo.dll`


* **静态库** 适用于不需要频繁更新库的场景，或者当程序需要部署到没有预装共享库的环境中时。
* **动态库** 更适合当多个应用程序需要共享同一个库时，或者你希望在不重新编译程序的情况下更新库文件。

##### 4. **动态库与静态库的加载方式**

* **动态库的调用流程：**

  * 编译时链接 `import.lib` 文件（Windows）或 `.so` 文件（Linux）；
  * 运行时加载对应的 `.dll` 或 `.so` 文件；
  * 如果使用动态链接的库，操作系统会在程序启动时查找并加载相应的动态库（可能通过 `LD_LIBRARY_PATH`、`PATH` 或指定的 `rpath`）。

* **静态库的调用流程：**

  * 在编译时，静态库的代码会直接嵌入到可执行文件中；
  * 因为静态库是提前链接的，所以运行时不需要额外加载库文件。

> [!abstract] `std::move`的作用，`std::move`失效的场景？
> 将一个对象的资源从一个地方转移到另一个地方，而不需要进行昂贵的深拷贝。它主要用于**将一个对象转换为右值引用**，以启用移动语义
> - **移动语义**：移动语义指的是通过转移对象的资源（如堆内存、文件句柄等）来避免不必要的深拷贝，从而提高程序的效率，尤其在处理临时对象时
> 
> **失效场景**：
> - 移动后访问源对象
> - 移动构造/赋值函数不存在
> - 对临时对象使用 `std::move`
> - 对常量对象使用 `std::move`
> - `std::move` 与 `std::swap` 的不兼容



> [!abstract] 构造函数能否为虚函数？
> - **对象尚未完全构造时无法调用虚函数：**
> 	在派生类的构造函数执行时，基类的构造函数首先被调用。此时，派生类的成员尚未被构造，类的实例还不完整。如果构造函数是虚函数，系统会尝试根据对象的动态类型来调用虚函数。这意味着在对象构造过程中的某个时刻，程序会尝试调用派生类的虚函数，而此时派生类的构造函数尚未执行，导致无法访问派生类的成员
> 	因此，虚函数需要一个已完全构造的对象才能正常工作，但构造函数无法保证此时对象已完全构造
> - **类的虚表（vtable）尚未建立：**  
> 	虚函数依赖于虚表（vtable）来实现运行时多态。虚表在对象构造过程中是在基类的构造函数中建立的，而在派生类的构造函数中才会被完善。如果在构造函数中调用虚函数，虚表可能还未建立完全，导致调用到不正确的函数实现，甚至导致程序崩溃



> [!abstract] 什么函数不可以是虚函数？
> 1. **构造函数 (Constructor)**
> 	- 在构造对象时，对象的动态类型尚未完全建立，虚表（vtable）尚未切换到派生类版本
> 	- 如果构造函数是虚函数，调用将无法确定具体的实现，违背了构造过程的语义
> 2. 静态成员函数 (static member function)
> 	- 静态成员函数没有 `this` 指针
> 	- 虚函数是基于对象的动态类型来通过虚表解析的，而 `static` 成员函数不依赖对象，因此无法是虚函数
> 3. **内联函数 (inline) [可但无意义]**
> 	- 严格来说，`inline` 修饰符与 `virtual` 不冲突，但“内联”与“虚函数调用的动态分派”语义相反
> 	- 当通过对象（非引用或指针）直接调用虚函数时，编译器可能静态解析并内联
> 	- 当通过基类指针/引用调用时，必须进行虚表查找，无法内联
> 	- 因此将虚函数声明为 `inline` 虽然语法合法，但通常不会内联
> 4. **模板函数（成员函数模板）**
> 	- 类的 **普通成员函数模板** 不能是虚函数
> 	- 原因：虚表需要在编译期确定每个虚函数的签名，但模板函数的实例化发生在使用时，编译器无法为每个潜在的模板参数实例生成虚表项
> 5. `constexpr` 修饰的成员函数

## `[!!abstract:什么是索引下推(Index Pushdown)]`

- 索引下推，又称“索引条件下推”（Index Condition Pushdown, ICP）或更广义的“谓词下推”（Predicate Pushdown）
- 是一种**尽早过滤、减少无用数据访问**的优化技术
- 是将 SQL 查询中的过滤条件尽量提前到索引扫描或存储层去执行，从而*减少回表*（或全表扫描）所需访问的数据量，提高查询性能 
- 对关系型数据库，多见于二级索引的条件下推（MySQL ICP） 
- 对现代大数据存储引擎，则演化为更丰富的谓词下推、聚合下推等，都是在存储层尽可能“吃掉”更多数据处理工作，减少网络和内存负担，从而提升整体查询性能

---

### 一、概念与原理

1. **传统索引访问流程**  
   - 在未做下推优化时，数据库在使用二级索引（非聚簇索引）查询时，会先按照索引 key 匹配到一批符合索引列的记录指针（rowid 或主键）
   - 然后对每一个指针执行回表（到聚簇索引或数据页）以读取完整行，再在完整行上再做剩余的 WHERE 条件过滤  

2. **索引下推后的访问流程**  
   - 在扫描二级索引的过程中，就将那些只涉及索引列的过滤条件（Index‐only predicates）在索引层先行判断，只有真正满足条件的指针才被返回用于回表
   - 这样能够大幅度减少回表次数，减少磁盘 I/O 和 CPU 解码开销

示意图：
``` lino:no
┌───────────────┐         ┌───────────┐         ┌──────────┐  
│  二级索引页   │----(1)->│ 条件Ⅰ筛选│----(2)->│ 回表取行 │  
└───────────────┘         └───────────┘         └──────────┘  
         │                                        ↑  
         └─────────(3) 剔除不匹配─────────────────┘  

```

1. 在索引页遍历时即判断（下推）只依赖索引列的条件
2. 满足的才送到回表阶段 
3. 不满足的直接丢弃，不访问数据页

---

### 二、MySQL 中的 Index Condition Pushdown

- 从 MySQL 5.6.12 开始支持 ICP。  
- 只对 **二级索引** 生效，且仅针对 WHERE 中只涉及索引列的部分条件。  
- 打开方式：默认打开，可用 `SET optimizer_switch='index_condition_pushdown=on';` 手动控制。  
- EXPLAIN 中会出现 `Using index condition;` 提示。

示例：

```sql
CREATE TABLE t (
  a INT,
  b INT,
  c VARCHAR(20),
  INDEX idx_ab(a, b)
);
-- 查询 WHERE a=10 AND b>5 AND c='foo'
EXPLAIN
SELECT * FROM t
WHERE a = 10 AND b > 5 AND c = 'foo';
```

- **下推条件**：`a=10 AND b>5`，因为它们都在索引 `idx_ab` 上  
- **剩余回表条件**：`c='foo'`

---

### 三、更广义的谓词下推

在现代分布式/列式存储系统（如 `TiDB, ClickHouse, Spark SQL, Parquet` 等）中，谓词下推会延伸到：

- **页面/区间剪裁**（Zone‐map 或 min/max Skip）：在数据块元数据（min/max）上提前过滤  
- **列存储下推**：只读取列文件中满足条件的行号或位图  
- **Coprocessor/Storage 下推**：把算子（Filter、Projection、聚合）下推到存储节点，让存储层直接返回部分聚合结果  

---

### 四、优点与适用场景

优点  
- 减少回表 I/O、降低磁盘 IO 及网络带宽消耗  
- 降低解码和行构建开销  
- 提升查询吞吐与响应速度

适用场景  
- 二级索引查询，且查询条件里既有索引列又有非索引列  
- 多列复合索引查询中，索引列部分可下推  
- 分布式/列式存储引擎中，复杂过滤或聚合能在存储层并行完成

> [!abstract] C++中`{cpp}class`和`{cpp}struct`相较于C语言中能够添加成员函数, 进行继承, 函数重载等操作, 那么对于`{cpp}union`类型,能否进行继承以及定义成员函数?
> *能够定义成员函数*, 不能继承, 默认访问修饰为`public`. 
> 
> 不过，**C++ 中的 `union` 定义成员函数时存在一些限制**，主要是由于它要求所有成员共享内存空间，因此不允许像 `class` 或 `struct` 那样拥有非静态数据成员的构造函数、析构函数或虚函数. 同时应该注意：
> - `union` 的所有数据成员共享同一块内存，因此它不能有构造函数和析构函数, 内存管理问题
> - 可以为 `union` 定义普通的成员函数，但这些函数的操作不能直接依赖于成员变量的生命周期

> [!abstract] `{c}enum` 和`{cpp}enum class`呢? 能否继承?
> 
> `enum`是一种类型, `enum class`是更加严格和安全的类型. 都不能继承或声明成员函数.
> 两者区别: 传统的 `enum` 会将枚举成员引入到全局作用域，而 `enum class` 的成员只在 `enum class` 类型的作用域内有效
