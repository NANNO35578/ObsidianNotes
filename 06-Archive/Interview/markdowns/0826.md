# 视频中I帧, P帧, B帧都表示什么?

[参考](https://zh.wikipedia.org/zh-cn/MPEG-2#%E8%A6%96%E8%A8%8A%E7%BC%96%E7%A0%81%E6%A6%82%E8%BF%B0) 
MPEG-2视频通常包含多个[GOP](https://zh.wikipedia.org/wiki/%E5%9C%96%E5%83%8F%E7%BE%A4%E7%B5%84 "图像组群")（Group Of Pictures），每一个GOP包含多个帧（frame）
帧的帧类（frame type）通常包括I-帧（I-frame）、P-帧（P-frame）和B-帧（B-frame）
<strong style="color:#e67e80">其中I-帧采用帧内编码，P-帧采用前向估计，B-帧采用双向估计</strong>

*I帧图像采用帧内编码方式*，仅使用本身的画面资料进行空间的冗馀去除，并没有参考其他画面的资料，我们称为Intra模式宏块（Intra Mode Macro-block）。在I帧图像中，所有的宏块皆为Intra模式宏块。*I帧图像可以做为视频资料流中的索引点*，也是提供随机存取能力的主要来源。I画面通常在视频序列或画面群组的第一张，解码时I画面可独立解码，并做为P及B画面的参考影像的来源。由于不须参考其他画面，因此无法得到消除时间上冗馀的好处，因此压缩率较差。

*P帧和B帧图像采用帧间编码方式*，即同时利用了空间和时间上的相关性。*P帧图像会使用参考画面*（Reference Picture），这些参考画面可为该帧*前面最近的*I帧或P帧。编码时，在P帧中的宏块，若能在参考画面上找到相对应的宏块，则用动态补偿方式做预测编码（Predictive Coding）；若找不到，则以Intra模式做编码。由于加入消除时间上冗馀的技术，因此其编码效率较高。*B帧图像采用双向时间预测*，会使用到前面及后面两个方向参考画面的资料。如同P帧一样，可以大大提高压缩倍数。值得注意的是，由于B帧图像采用了未来帧作为参考，因此MPEG-2编码码流中图像帧的传输顺序和显示顺序是不同的。 B帧拥有最高的编码效率，然画质最差，故本身不再做为其他预测编码用。

# 项目中的解码流程

> 1. **网络层**：拉取 `.m3u8` → `.ts` 切片 → HTTP 输入流。
> 2. **解复用层**：`avformat_open_input()` + `av_read_frame()` → 压缩包 → 音视频队列。
> 3. **解码层**：
>    * H.264 → YUV 帧
>    * AAC → PCM 帧
> 4. **同步**：基于 `PTS`，保持音视频时钟一致。
> 5. **渲染层**：
>    * 视频：YUV → OpenGL 纹理 → 屏幕
>    * 音频：PCM → SDL 音频回调 → 声卡

##### 1. 网络层：拉取 HLS 切片
* 使用 **Nginx-http-hls-module** 在服务器端对视频进行切片分发（生成 `.m3u8` 索引和 `.ts` 切片）。
* 客户端通过 **FFmpeg 的 libavformat/hls.c** 解析 `.m3u8` 文件。
* 内部逻辑：
  * 自动解析 `#EXTINF` 字段，按顺序通过 **HTTP 协议** 拉取 `.ts` 切片。
  * 维护一个 `AVIOContext → URLProtocol(http)` 抽象，使解复用层像读本地文件一样处理网络流。

##### 2. 解复用层：拆分 TS 流
* 调用 `avformat_open_input()` 打开流输入，并通过 `avformat_find_stream_info()` 获取媒体信息，得到 `AVFormatContext`。
* 遍历流，找到 **视频流（H.264）和音频流（AAC）** 索引。
* 进入循环：
  * 调用 `av_read_frame()` 读取一个 `AVPacket`（压缩数据包）。
  * 按流类型分发到 **视频队列** 或 **音频队列**（`PacketQueue`），等待解码。

##### 3. 解码层：压缩数据 → 原始帧
 **视频解码**
  * 使用 `avcodec_find_decoder(AV_CODEC_ID_H264)` 找到解码器。
  * 调用 `avcodec_open2()` 打开解码器上下文。
  * 视频解码线程（`video_thread`）中不断从队列取 `AVPacket`，调用 `avcodec_send_packet()` + `avcodec_receive_frame()`，得到 `AVFrame (YUV)`。

 **音频解码**
  * 使用 `avcodec_find_decoder(AV_CODEC_ID_AAC)` 打开解码器。
  * 在音频回调函数 `audio_callback()` 中解码数据，得到 `AVFrame (PCM)`。
  * 同时根据音频参数配置 SDL 音频设备：
    * `SDL_OpenAudioDevice()` 打开音频输出设备。
    * 设备默认是暂停状态，需要 `SDL_PauseAudioDevice(audioID, 0)` 才开始回调取数据并播放。

##### 4. 时间同步
 在 **视频解码线程 (`video_thread`)** 中：
  * 根据 `PTS`（显示时间戳）进行音视频同步。
  * 若视频过快，需要等待音频进度；若视频滞后，则丢帧。
  * 确保画面和声音同步输出。

##### 5. 渲染层：显示 & 播放
 **视频渲染**
  * 解码得到的 YUV 数据先传入 OpenGL。
  * 在着色器中完成 YUV → RGB 转换，生成纹理（Texture），最终绘制到屏幕。

 **音频播放**
  * SDL 音频设备会自动回调 `audio_callback()` 获取 PCM 数据。
  * SDL 播放线程从解码队列中取数据，送到声卡进行播放。

# 软解码和硬解码
*硬解码*：使用专用硬件模块来完成视频解码任务.
例如:
- [Intel Quick Sync Video](https://en.wikipedia.org/wiki/Intel_Quick_Sync_Video)（核显）;
- NVIDIA [NVDEC](https://en.wikipedia.org/wiki/NVDEC)/[NVENC](https://en.wikipedia.org/wiki/NVENC)（独显）;
- AMD VCE/UVD（A卡）;
- 手机上的 SoC 中的 VPU（视频处理单元）

优点：解码速度快，CPU不参与或很少参与；
缺点:不是支持所有格式，eg AV1；依赖显卡驱动；不容易调试；

*软解码*：使用CPU（通用处理器）通过软件算法来解码视频.
例如:
- FFmpeg（libavcodec）
- VLC、PotPlayer、MPV 等播放器内置解码器
- Chrome、Edge 浏览器内置解码器

优点：理论上支持所有格式，只要编码器更新就能解；灵活性高 ，可自定义解码参数，适合调试、转码、滤镜处理；跨平台，不依赖特定硬件，任何设备只要有CPU就能运行
缺点：CPU占用高，播放高码率视频可能影响其他程序运行

# `{cpp}constexpr`和`{c}const`区别

 `[!!sprout:constexpr]` : 修饰真正的常量, 编译期会计算出来, 整个运行过程不会被改变, 可修饰函数, 返回值会尽可能在编译期被计算当作一个常量, 若不能计算出来, 就是一个普通函数. 可赋值`const`常量

> [!example] `{cpp}constexpr` 与`{c}const` 的区别
> *const* :
>    - 主要用于指明变量的值在初始化后就不应该被改变
>    - `const` 变量的值可以在运行时确定,也可以在编译时确定
>    - `const` 变量的初始化可以是任意复杂的表达式<br>
>  
> *constexpr* : 是 C++11 新引入的关键字, 用于声明表达式(函数)为编译时常量, 保证了变量或函数在编译时就已经确定了值,使得它们可以用在需要编译时常量表达式的场景中, 例如数组的大小
>    - `constexpr` 变量或函数必须在编译时就能确定其值或结果
>    - `constexpr` 可以用于函数和构造函数,可以创建在编译时就能计算出结果的函数和对象
>    - `constexpr` 变量或函数的初始化表达式必须足够简单,以便编译器能够在编译时求值



# volatile关键字作用
- 告诉编译器变量随时发生变化, 每次访问得从内存中读取, 而不是从寄存器访问. 从而保证CPU寄存器值与内存值一致
- 写优先于读. 同时避免编译器优化, 导致多线程出现运行问题.
 
<strong style="color:#e67e80">并非避免线程并发数据竞争问题</strong>, 也就是不能做到线程同步

# L/F线程池怎么实现的
线程池中有两个主要角色:
- leader: 领导者.
- follower: 追随者.

*主要逻辑*: 线程池中无论何时都只有一个leader线程, 若干follower线程, 同时可存在若干worker线程.
- 当有任务到来时, 由leader线程接收到任务相关数据, 同时提升一个follower为后继leader, 自己则退化为worker线程进行任务处理.
- 当任务处理完成后, worker线程将提升为follower线程.

主要对比与生产者消费者模式, 数据可直接交由接收线程处理, 而无需进行线程间数据通信.

`{c}tmp_buf = mmap(file, len);  write(socket, tmp_buf, len);`

通过使用 mmap 减少了一半内核必须复制的数据量.


> [!bug] *这种改进也有代价*使用 mmap+write 会有一些隐藏的陷阱: 
> 例如，当映射了一个文件并调用 write 时，如果另一个进程同时截断了这个文件，你的 write 系统调用会被总线错误信号 SIGBUS 中断，因为你执行了错误的内存访问
> 该信号的默认行为是杀死进程并生成 core dump——显然不是网络服务器所期望的操作

1. 屏蔽信号
2. 利用内核的文件租约（在 Windows 中称为“机会锁”）:

```c
if(fcntl(fd, F_SETSIG, RT_SIGNAL_LEASE) == -1) {
    perror("kernel lease set signal");
    return -1;
}
/* l_type 可以是 F_RDLCK F_WRLCK */
if(fcntl(fd, F_SETLEASE, l_type)){
    perror("kernel lease set type");
    return -1;
}
```
