## 问题 1：全文检索（Full-Text Search）

**Q10.** 用户希望在网盘里搜“某关键词”，能在文档、笔记、文件名、分享说明里快速定位。你如何设计全文检索方案？

**A10.**  
1. 架构选型  
   - 用专门的全文检索引擎，如 **Elasticsearch** 或 **OpenSearch**；  
   - 定期或实时将元数据与文档内容（PDF、Office、TXT）送入索引。  

2. 文档解析  
   - 后台服务调用 Apache Tika / LibreOffice headless 将各格式文件转换为纯文本；  
   - 抽取文本和元属性（作者、日期、标签），构建文档 JSON。  

   ```json title:"索引结构示例"

         "user_id":   { "type": "long" },

         "content":   { "type": "text", "analyzer": "ik_smart" },
         "tags":      { "type": "keyword" },
         "created_at":{ "type": "date" }
       }
     }
   }
   ```  

   - 支持布尔、模糊、短语、前缀查询；  
   - 高频词高亮显示、分页与排序，按相关度或时间。

## 问题 2：离线/多端同步与冲突解决

**Q11.** 如果要支持多客户端（桌面/移动/Web）离线编辑并与云端同步，如何设计同步协议和冲突检测/解决机制？

**A11.**  
1. 同步协议  
   - **基于操作日志**（Operation Log）：记录所有增删改操作（OP）  
     - OP 中包括 `op_id`, `timestamp`, `user_id`, `file_id`, `action`, `delta`  
   - 客户端上线后拉取最新 OP，按时间戳或逻辑时钟（Lamport/Vector Clock）顺序重放。  

2. 冲突检测  
   - 同一文件的两个 OP 时间戳交叉，且作用区间重复 → 视为冲突。  
   - 客户端本地维护 Vector Clock，与服务器合并时做对比。  

3. 冲突解决  
   - **自动合并**：对文本文件可使用三方合并算法；  
   - **用户干预**：对二进制/复杂文件生成冲突版本（`file_conflict_⟨时间⟩.ext`），通知用户手动选择。

## 问题 3：灾备与高可用（Disaster Recovery & High Availability）

**Q13.** 如果要确保你的网盘在单点故障、数据中心灾难甚至区域性宕机时仍能可用，并且丢失数据最小，你如何设计系统的高可用与灾备方案？

**A13.**  
1. 数据存储多副本  
   - MySQL：采用主主或多主复制（Group Replication/Percona XtraDB Cluster），跨机房同步；  
   - 对象存储：使用 Ceph/RADOS Gateway 或多区域 S3 Replication，将文件块在不同可用区保存。  
2. 请求层冗余  
   - 前端（nginx/Load Balancer）：多台部署，Health check + Keepalived/VRRP 实现 VIP 漂移；  
   - DNS：配置多条 CNAME/ALIAS 指向不同地域的 LB，配合 DNS 低 TTL。  
3. 自动故障切换  
   - 数据库：用 Orchestrator/Patroni 自动监测主节点健康，发生故障自动切换并通知应用层；  
   - 应用服务：Kubernetes + StatefulSet/Deployment，Pod 无状态或带 PV，Replica 数 ≥ 3，节点挂掉自动重启。  
4. 灾难恢复（DR）  
   - 异地冷/热备：定时将数据库 binlog 或快照同步到二级灾备机房；  
   - 持续快照：对象存储开启多版本（versioning），快照周期性备份到其他集群；  
   - 演练：定期 DR 演练、恢复演练，测试 RTO（恢复时间）和 RPO（数据丢失窗口）。

## 问题 4：限流与资源配额（Rate Limiting & Quotas）

**Q14.** 当海量用户同时请求上传、下载或视频预览时，如何在保证系统稳定的前提下对用户做限流和隔离？  

**A14.**  
1. 粒度与策略  
   - **全局限流**：控制整个系统的 QPS/带宽上限；  
   - **租户/用户级限流**：按照用户 ID 或租户划分令牌桶（Token Bucket）或漏桶（Leaky Bucket）；  
   - **接口/功能级**：对上传、下载、预览各自设不同阈值。  
2. 实现方式  
   - 中央限流：使用 Redis + Lua 脚本原子操作计数令牌；  
   - 边缘限流：在 CDN 或 API 网关（Kong/Envoy）侧打点过滤；  
   - 本地缓存：在应用层维护本机令牌桶，定期与 Redis 同步。  
3. 配额管理  
   - 存储配额：数据库记录每个用户已用/总配额，上传前检查；  
   - 并发配额：限制单用户最大并发上传任务数或连接数，超出直接拒绝或排队。  
4. 限流降级  
   - 超阈值后可返回 `429 Too Many Requests`，提示客户端重试；  
   - 针对急用场景提供付费“加速包”临时提升限额。

## 问题 5：HLS 播放时偶现花屏或卡顿

**场景：** 用户在手机端视频预览经常卡顿，断断续续花屏，日志里 nginx 和 FFmpeg 都没报错。

**问：**  
1. 你如何一步步定位问题？  
2. 如果找到了瓶颈，打算怎么优化？

## 问题 6：数据库表结构变更导致线上熔断

**场景：**  
你要给 `files` 表加一个新字段 `checksum VARCHAR(64)`，在业务高峰期执行了 `ALTER TABLE`，结果几分钟后应用开始报 `Lock wait timeout`，大量请求超时。

**问：**  
1. 为何会出现这种情况？  
2. 如何做零停机演进？  

**参考答案：**  
1. 原因  
   - MySQL 在执行 DDL 时对整表加了元数据锁（MDL），阻塞所有读写；高并发下连锁等待导致超时。  
2. 零停机方案  
   - 使用 **在线DDL** 工具：Percona Toolkit 的 `pt-online-schema-change` 或阿里的 `gh-ost`，利用触发器和 shadow table 逐步同步数据；  
   - 先创建新表并异步复制全量/增量，再切流量、替换表名、删除旧表；  
   - 或者使用 MySQL 8.0+ 的原生 `ALGORITHM=INPLACE, LOCK=NONE`（若支持）执行在线 DDL。

## 问题 7：离线修改冲突率特别高

**场景：**  
桌面客户端支持离线编辑文件夹/文件，结果线上调查发现 30% 的同步任务因为冲突需要用户手动解决，体验太差。

**问：**  
1. 为什么冲突这么频繁？  
2. 怎么从协议和实现层面降低冲突率？  

**参考答案：**  
1. 原因  
   - 客户端离线期间多端对同一目录做并行重命名、移动、删除等操作；  
   - 同步机制只按文件级多版本，不做细粒度操作合并。  
2. 优化  
   - 改用 Operation‐based 同步：把文件操作（rename/move/write）序列化成 OP Log；  
   - 采用 CRDT（如 Yjs、Automerge）对目录结构做无冲突合并；  
   - 冲突检测时引入**优先级**（ 最后修改时间＋来源端 ID）自动合并重命名/移动，只对实际内容冲突才人工介入。

## 问题 1：Epoll + 线程池模型

**Q1.** 请描述你在 Linux（WSL）环境下，如何基于 epoll 和线程池实现高并发 I/O 的。重点说明：

- epoll 的工作流程  
- 线程池如何接收并处理请求  
- 如何保证并发安全与负载均衡  

**A1.**  
1. epoll 工作流程  
   2. 初始化：通过 `epoll_create1()` 创建 epoll 实例。  
   3. 注册事件：使用 `epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event)` 将监听 socket 和已连接 socket 加入 epoll 监听列表（关注 `EPOLLIN`、`EPOLLOUT` 等事件）。  
   4. 事件循环：主线程调用 `epoll_wait(epfd, events, MAX_EVENTS, timeout)` 阻塞等待事件发生。  

5. 线程池设计  
   - **任务队列**：主线程（I/O 线程）接收到就绪事件后，将对应的 socket fd 或完整的请求信息封装成 Task，推入一个并发安全的任务队列（使用互斥锁 + 条件变量或无锁队列）。  
   - **工作线程**：若干工作线程从队列中取 Task，执行具体的业务逻辑（解析 HTTP/WebSocket、读写文件、数据库操作等），并在处理完毕后将响应通过异步写回主线程或直接回写。  

3. 并发安全与负载均衡  
   - **数据保护**：共享队列用互斥锁+条件变量保护；对每个连接的数据上下文（如读写缓冲区、状态机）均封装到独立结构体，避免对象间数据竞争。  
   - **负载分配**：线程池初始化时工作线程数可按 CPU 核数 × 1.5 动态设置；队列长度和饱和度检测可监控并扩缩容或者拒绝策略。

## 问题 2：断点续传（Breakpoint Resume）

**Q2.** 你的项目里断点续传是如何实现的？请说明：

- 客户端如何分块上传/下载  
- sqlite 在其中的角色和表结构设计  
- 恢复上传时，如何保证数据完整性  

**A2.**  
1. 分块策略  
   - 将大文件按固定大小（如 4MB）分块，每块用 MD5 计算块校验。  
   - 客户端在上传前查询本地 sqlite，检查哪些块已上传完成，跳过这些块。  

2. sqlite 角色  
   - **表结构示例**：  
     ```sql
     CREATE TABLE UploadTask (
       task_id   TEXT PRIMARY KEY,   -- 文件唯一标识（如文件 MD5）
       file_path TEXT,
       total_size INTEGER,
       chunk_size INTEGER,
       uploaded_chunks BLOB         -- 已成功上传块的位图或列表
     );
     ```  
   - 客户端每上传完一块，就更新对应记录：`UPDATE UploadTask SET uploaded_chunks = ? WHERE task_id = ?;`  

3. 恢复与完整性  
   - 客户端启动或重试时读取 `uploaded_chunks`，只对缺失块重新请求。  
   - 服务端在收到每块后，比对客户端 MD5 校验并存储到临时文件；全部块到齐后拼接并做整体 MD5 校验。

## 问题 3：HLS + nginx 视频预览

**Q3.** 解释项目中如何利用 nginx HLS 模块支持视频预览，描述从用户上传视频到前端播放的完整流程。

**A3.**  
1. 用户上传视频到服务器后，后台触发一个转码任务（可同步/异步）。  
2. 使用 FFmpeg 将上传的源文件转码为 HLS 格式：  
   ```
   ffmpeg -i input.mp4 -codec: copy \
     -start_number 0 -hls_time 10 -hls_list_size 0 \
     -f hls /var/www/hls/{video_id}.m3u8
   ```  
3. nginx 配置：
   ```nginx
   location /hls/ {
     types { application/vnd.apple.mpegurl m3u8; video/mp2t ts; }
     root /var/www;
     add_header Cache-Control no-cache;
   }
   ```  
4. 前端播放器（如 video.js）请求 `/hls/{video_id}.m3u8`，得到播放列表后顺序拉取 `.ts` 分片并播放。

## 问题 4：FFmpeg + Qt/OpenGL + SDL

**Q4.** 你在客户端使用 FFmpeg 进行视频解码，Qt 的 OpenGL 模块渲染视频帧，SDL 播放音频。请说明：

- 解码线程与渲染/播放线程之间如何同步  
- 如何保证 AV 同步（音视频不同步时如何处理）  

**A4.**  
1. 解码线程  
   - 独立线程不断调用 `av_read_frame()` → `avcodec_send_packet()` → `avcodec_receive_frame()`，将得到的 `AVFrame`（视频）或 `AVFrame`（音频）分别推入两个线程安全队列：`videoQueue`、`audioQueue`。  

2. 渲染/播放线程  
   - **视频渲染**：Qt+OpenGL 线程不断从 `videoQueue` 取帧，用 `QOpenGLTexture` 上传到 GPU，并在 `paintGL()` 中绘制。  
   - **音频播放**：SDL 回调函数中从 `audioQueue` 取帧，交给 SDL 混音并输出。  

3. AV 同步  
   - 主时钟以音频时钟为主（SDL 回调时间戳）；每渲染一帧都对比音频时钟（`audio_clock`）和帧的 `pts`：  
     - 若 `video_pts > audio_clock + threshold`，则视频线程短暂休眠；  
     - 若 `video_pts < audio_clock - threshold`，则丢弃或快速渲染跳帧。

## 问题 5：单例模式与中介者模式

**Q5.** 核心类采用单例模式，网络类与核心类的数据转发通过中介者完成。请解释：

- 单例模式如何保证线程安全  
- 中介者模式的职责和实现思路  

**A5.**  
1. 单例模式（C++11 版）  
   ```cpp
   class CoreManager {
   public:
     static CoreManager& instance() {
       static CoreManager inst;  // C++11 局部静态变量线程安全
       return inst;
     }
     // 禁止拷贝和赋值
     CoreManager(const CoreManager&)=delete;
     CoreManager& operator=(const CoreManager&)=delete;
   private:
     CoreManager() { /* 初始化 */ }
   };
   ```  

2. 中介者模式  
   - **职责**：解耦网络模块（负责 I/O）与核心逻辑模块，通过一个 `Mediator` 对象转发消息。  
   - **实现思路**：  
     ```cpp
     class Mediator {
       NetworkModule* net;
       CoreManager* core;
     public:
       void registerNetwork(NetworkModule* n) { net = n; }
       void registerCore(CoreManager* c)   { core = c; }
       // 当收到网络请求
       void onRequest(const Request& req) {
         core->handleRequest(req);
       }
       // 核心响应后
       void onResponse(const Response& resp) {
         net->sendResponse(resp);
       }
     };
     ```

## 问题 6：安全性与 MD5

**Q6.** 项目使用 MD5 对部分数据加密。MD5 在现代安全需求下有哪些缺陷？如果要增强安全性，你会采用哪些措施？

**A6.**  
- MD5 已被证明存在 **碰撞漏洞**，不适合密码学安全场景。  
- **改进方案**：  
  1. 使用 **SHA-256** 或更强的散列算法（如 SHA-3）。  
  2. 对重要数据（如用户密码）加盐并使用 PBKDF2、bcrypt、scrypt 进行多轮迭代哈希。  
  3. 对文件完整性校验，可以用 SHA256+ HMAC 进行签名，防止篡改。

## 问题 8：文件多版本管理（Versioning）

**Q8.** 如果要给网盘加上文件版本管理功能，你如何设计存储方案和元数据结构，既能节省空间又能快速回滚？

**A8.**  
1. 存储方案  
   - **增量快照**：  
     - 对每次文件修改生成增量 diff（如二进制块差分），存为增量块；  
     - 最新版本保留全量快照，历史版本通过应用 diff 回滚。  
   - **内容寻址存储**（CAS）：  
     - 将文件分块（如 4MB），按内容 Hash（SHA-256）命名存储；  
     - 不同版本间共享相同块。  

2. 元数据结构  
   ```sql
   CREATE TABLE FileVersions (
     file_id       BIGINT,
     version_id    INT AUTO_INCREMENT,
     parent_ver    INT,            -- 指向上一个版本
     is_full       BOOLEAN,        -- 是否全量快照
     chunk_list    JSON,           -- 块哈希数组
     created_at    DATETIME,
     PRIMARY KEY(file_id, version_id)
   );
   ```  
3. 回滚逻辑  
   - 取指定版本的 `chunk_list`，按顺序组装；如遇增量，可递归获取 parent 直至全量。  
   - 用缓存（Redis）或本地磁盘加速常用版本读取。

## 问题 9：文件/块级去重（Deduplication）

**Q9.** 面对海量用户的大文件上传，如何在服务端实现文件级和块级去重，提高存储利用率？

**A9.**  
1. 文件级去重  
   - 客户端上传前先计算全文件 SHA-256；  
   - 服务端查重：若已有相同 Hash，则直接在元数据层关联，无需再次上传。  

2. 块级去重  
   - 将文件按固定或内容定义分块（如 Rabin 指纹分块）；  
   - 每块计算 SHA-256，上传时并行检查：  
     - 未命中再上传并存储；  
     - 命中则引用已有块。  

3. 索引与引用计数  
   ```sql
   CREATE TABLE Chunks (
     chunk_hash   CHAR(64) PRIMARY KEY,
     size         BIGINT,
     ref_count    INT,
     storage_path VARCHAR(256)
   );
   ```  
   - 上传完成后 `INSERT … ON DUPLICATE UPDATE ref_count = ref_count + 1`；  
   - 删除时 `ref_count--`，为 0 时垃圾回收。

## 问题 10：全文检索（Full-Text Search）

**Q10.** 用户希望在网盘里搜“某关键词”，能在文档、笔记、文件名、分享说明里快速定位。你如何设计全文检索方案？

**A10.**  
1. 架构选型  
   - 用专门的全文检索引擎，如 **Elasticsearch** 或 **OpenSearch**；  
   - 定期或实时将元数据与文档内容（PDF、Office、TXT）送入索引。  

2. 文档解析  
   - 后台服务调用 Apache Tika / LibreOffice headless 将各格式文件转换为纯文本；  
   - 抽取文本和元属性（作者、日期、标签），构建文档 JSON。  

3. 索引结构示例  
   ```json
   {
     "mappings": {
       "properties": {
         "file_id":   { "type": "long" },
         "user_id":   { "type": "long" },
         "filename":  { "type": "text", "analyzer": "ik_max_word" },
         "content":   { "type": "text", "analyzer": "ik_smart" },
         "tags":      { "type": "keyword" },
         "created_at":{ "type": "date" }
       }
     }
   }
   ```  
4. 搜索体验  
   - 支持布尔、模糊、短语、前缀查询；  
   - 高频词高亮显示、分页与排序，按相关度或时间。

## 问题 11：离线/多端同步与冲突解决

**Q11.** 如果要支持多客户端（桌面/移动/Web）离线编辑并与云端同步，如何设计同步协议和冲突检测/解决机制？

**A11.**  
1. 同步协议  
   - **基于操作日志**（Operation Log）：记录所有增删改操作（OP）  
     - OP 中包括 `op_id`, `timestamp`, `user_id`, `file_id`, `action`, `delta`  
   - 客户端上线后拉取最新 OP，按时间戳或逻辑时钟（Lamport/Vector Clock）顺序重放。  

2. 冲突检测  
   - 同一文件的两个 OP 时间戳交叉，且作用区间重复 → 视为冲突。  
   - 客户端本地维护 Vector Clock，与服务器合并时做对比。  

3. 冲突解决  
   - **自动合并**：对文本文件可使用三方合并算法；  
   - **用户干预**：对二进制/复杂文件生成冲突版本（`file_conflict_⟨时间⟩.ext`），通知用户手动选择。

## 问题 12：CDN 加速与边缘分发

**Q12.** 为了提高全球用户下载和 HLS 播放的速度，你会如何接入 CDN？需要注意哪些缓存策略和安全设计？

**A12.**  
1. CDN 接入  
   - 将静态资源（文件下载、`.m3u8`、`.ts`）暴露在如 `cdn.example.com` 子域名；  
   - 在 nginx 层配置 `proxy_pass` 或直接用 Object Storage + CDN。  

2. 缓存策略  
   - 对不可变资源（文件块、视频分片）设置强缓存：`Cache-Control: max-age=31536000, immutable`；  
   - 对可变列表（目录 JSON、HLS 播放列表）用短时或 `no-cache` 强制校验。  

3. 安全防盗链  
   - **URL 签名**：对下载/流地址附带带过期时间的 HMAC 签名参数；  
   - **Referer 白名单** 或 **Token 验证**：在边缘校验合法性后才缓存/回源。

## 问题 13：灾备与高可用（Disaster Recovery & High Availability）

**Q13.** 如果要确保你的网盘在单点故障、数据中心灾难甚至区域性宕机时仍能可用，并且丢失数据最小，你如何设计系统的高可用与灾备方案？

**A13.**  
1. 数据存储多副本  
   - MySQL：采用主主或多主复制（Group Replication/Percona XtraDB Cluster），跨机房同步；  
   - 对象存储：使用 Ceph/RADOS Gateway 或多区域 S3 Replication，将文件块在不同可用区保存。  
2. 请求层冗余  
   - 前端（nginx/Load Balancer）：多台部署，Health check + Keepalived/VRRP 实现 VIP 漂移；  
   - DNS：配置多条 CNAME/ALIAS 指向不同地域的 LB，配合 DNS 低 TTL。  
3. 自动故障切换  
   - 数据库：用 Orchestrator/Patroni 自动监测主节点健康，发生故障自动切换并通知应用层；  
   - 应用服务：Kubernetes + StatefulSet/Deployment，Pod 无状态或带 PV，Replica 数 ≥ 3，节点挂掉自动重启。  
4. 灾难恢复（DR）  
   - 异地冷/热备：定时将数据库 binlog 或快照同步到二级灾备机房；  
   - 持续快照：对象存储开启多版本（versioning），快照周期性备份到其他集群；  
   - 演练：定期 DR 演练、恢复演练，测试 RTO（恢复时间）和 RPO（数据丢失窗口）。

## 问题 14：限流与资源配额（Rate Limiting & Quotas）

**Q14.** 当海量用户同时请求上传、下载或视频预览时，如何在保证系统稳定的前提下对用户做限流和隔离？  

**A14.**  
1. 粒度与策略  
   - **全局限流**：控制整个系统的 QPS/带宽上限；  
   - **租户/用户级限流**：按照用户 ID 或租户划分令牌桶（Token Bucket）或漏桶（Leaky Bucket）；  
   - **接口/功能级**：对上传、下载、预览各自设不同阈值。  
2. 实现方式  
   - 中央限流：使用 Redis + Lua 脚本原子操作计数令牌；  
   - 边缘限流：在 CDN 或 API 网关（Kong/Envoy）侧打点过滤；  
   - 本地缓存：在应用层维护本机令牌桶，定期与 Redis 同步。  
3. 配额管理  
   - 存储配额：数据库记录每个用户已用/总配额，上传前检查；  
   - 并发配额：限制单用户最大并发上传任务数或连接数，超出直接拒绝或排队。  
4. 限流降级  
   - 超阈值后可返回 `429 Too Many Requests`，提示客户端重试；  
   - 针对急用场景提供付费“加速包”临时提升限额。

## 问题 15：REST API 设计与版本管理

**Q15.** 如果你的网盘要对外提供开放 API，设计时如何保证易用、安全并且可演进？请谈谈接口设计和版本管理的思路。  

**A15.**  
1. 设计原则  
   - **资源导向**：用 `/users/{uid}/files/{fid}` 等 URI 表示资源；  
   - **动词语义化**：GET 取资源、POST 创建、PUT 完整更新、PATCH 局部更新、DELETE 删除；  
   - **统一响应**：JSON 包含 `code`/`message`/`data`，按 RESTful 错误码（4xx/5xx）。  
2. 版本控制  
   - **URI 版本化**：`/v1/files`，后续升级 `/v2/files`；  
   - **Header 版本化**：`Accept: application/vnd.example.v2+json`；  
   - **向后兼容**：新字段为可选、默认值兼容旧客户端；保持旧版本至少若干周期。  
3. 安全认证  
   - OAuth2.0 + JWT：Access Token 带过期时间，Refresh Token 刷新；  
   - Scope 控制：不同 Token 持有不同权限（读取、写入、分享）。  
4. 文档与测试  
   - 使用 OpenAPI/Swagger 自动生成文档与 SDK；  
   - 编写契约测试（Contract Tests），保证服务端变更不破坏客户端。

## 问题 16：日志、监控与分布式追踪

**Q16.** 在复杂的分布式网盘系统中，如何设计日志、监控和追踪方案，以便快速定位故障并优化性能？  

**A16.**  
1. 日志  
   - **结构化日志**：JSON 格式，字段包括 trace_id、span_id、user_id、请求路径、耗时、状态码；  
   - **集中收集**：Filebeat → Elasticsearch；或 Fluentd → Loki/Grafana；  
   - **日志切分**：按天/按服务切索引，避免单索引过大。  
2. 监控  
   - **指标采集**：Prometheus + Node Exporter / custom Exporter，监控 CPU、内存、I/O、QPS、延迟、错误率；  
   - **可视化**：Grafana 仪表盘展示 SLA、SLO；  
   - **告警**：基于 Prometheus Alertmanager，设置阈值告警（如 99% 响应时间 > 200ms）。  
3. 分布式追踪  
   - 接入 Jaeger/OpenTelemetry，在每个请求入口生成 trace_id，RPC/DB/File 调用都传递并记录 span；  
   - 在追踪界面查看请求链路、瓶颈 span、慢调用，快速定位性能热点。

## 问题 17：CI/CD 与自动化测试

**Q17.** 为了持续交付并保证新功能上线质量，你如何设计网盘项目的 CI/CD 流水线与测试策略？  

**A17.**  
1. 流水线架构  
   - **代码扫描**：PR 提交触发静态代码扫描（SonarQube、ESLint、Clang-Tidy）；  
   - **单元测试**：C++/Qt 用 Google Test，Python/JS 用对应框架，覆盖核心逻辑；  
   - **集成测试**：在 Docker Compose 或 Kubernetes 测试环境跑端到端场景（注册→上传→断点续传→下载）；  
   - **性能测试**：JMeter/Gatling 模拟并发、压力测试，设定 SLA 报告；  
   - **安全测试**：依赖漏洞扫描（Snyk、Trivy），接口渗透测试。  
2. 部署与回滚  
   - **蓝绿/滚动发布**：最小化灰度风险，发布前对一部分用户流量进行验证；  
   - **自动回滚**：发布后若监控告警触发（错误率或延迟突增），自动回滚到上一个版本；  
   - **基础镜像**：统一维护 CI/CD 镜像，内含编译环境、依赖库，保证环境一致性。

## 问题 18：上传接口突然 90% 报 500 错误

**场景：**  
前端监控突然发现上传接口（`/api/upload`）90% 返回 500，伴随日志里出现大量 `std::bad_alloc` 和超时。晚上 8 点后开始急速上升。

**问：**  
1. 你会如何快速定位问题根因？  
2. 提哪些临时缓解措施？  
3. 从架构上怎么彻底避免类似故障？

**参考答案：**  
1. 定位  
   - 查看机器 CPU/mem/I/O 使用曲线，是否因流量骤增耗尽内存或磁盘。  
   - 从 Nginx access/nginx_error、应用日志抓取 500 的上下文（请求大小、client IP、并发数）。  
   - 核实线程池队列是否堆积、epoll_wait 是否超时、sqlite 写入是否阻塞。  
2. 临时缓解  
   - 限流：在 Nginx 或 API 网关对并发上传做漏桶限流，返回 429 提示客户端稍后重试。  
   - 缩减并发：将线程池最大线程数、队列长度临时调小，避免过度竞争导致 OOM。  
   - 临时扩容：快速在容器/VM 上拉起更多实例，分摊流量。  
3. 长期方案  
   - 引入异步消息队列（Kafka/RabbitMQ）：上传请求先写入消息队列，再由后台消费者持久化，削峰填谷。  
   - 给 sqlite 写入加本地分片/持久化策略，或切换到更高性能的本地 KV（LMDB/RocksDB）做断点续传元数据。  
   - 增加监控告警——内存、队列长度超阈即刻触发扩容或降级限流。

## 问题 19：HLS 播放时偶现花屏或卡顿

**场景：** 用户在手机端视频预览经常卡顿，断断续续花屏，日志里 nginx 和 FFmpeg 都没报错。

**问：**  
1. 你如何一步步定位问题？  
2. 如果找到了瓶颈，打算怎么优化？  

**参考答案：**  
1. 定位思路  
   - 客户端侧：启用播放器 debug 模式，观察下载每个 `.ts` 分片的耗时、丢包率；  
   - CDN/NGINX：检查分片缓存命中率、后端回源延迟、带宽利用率；  
   - 后端：看 HLS 分片生成是否均匀（FFmpeg 转码耗时基线），是否出现 TS 丢失或延迟写入。  
2. 优化手段  
   - 调整 `.m3u8` 的 `#EXT-X-TARGETDURATION` 降低分片时长（如 10s → 5s），减小单片体积；  
   - 在 nginx 开启 HTTP/2 或 gRPC 以多路复用请求，加速多片并发拉取；  
   - CDN 层打点测速，必要时接入多家 CDN 做回源多路负载；  
   - 客户端预取：提前下载后续 2–3 片缓冲，降低网络抖动带来的卡顿。

## 问题 20：数据库表结构变更导致线上熔断

**场景：**  
你要给 `files` 表加一个新字段 `checksum VARCHAR(64)`，在业务高峰期执行了 `ALTER TABLE`，结果几分钟后应用开始报 `Lock wait timeout`，大量请求超时。

**问：**  
1. 为何会出现这种情况？  
2. 如何做零停机演进？  

**参考答案：**  
1. 原因  
   - MySQL 在执行 DDL 时对整表加了元数据锁（MDL），阻塞所有读写；高并发下连锁等待导致超时。  
2. 零停机方案  
   - 使用 **在线DDL** 工具：Percona Toolkit 的 `pt-online-schema-change` 或阿里的 `gh-ost`，利用触发器和 shadow table 逐步同步数据；  
   - 先创建新表并异步复制全量/增量，再切流量、替换表名、删除旧表；  
   - 或者使用 MySQL 8.0+ 的原生 `ALGORITHM=INPLACE, LOCK=NONE`（若支持）执行在线 DDL。

## 问题 21：跨区域多活导致文件列表不一致

**场景：**  
你部署了两套跨大区的网盘服务，A 区用户上传后 2 秒能在 A 区列表看到，B 区用户有时要等 10 分钟才同步。

**问：**  
1. 分析下根本原因？  
2. 如何保证“读后写一致”或可接受的“读-写延迟”SLA？  

**参考答案：**  
1. 根因  
   - 元数据写入后只是异步通过数据库或消息队列复制到 B 区，有网络波动、队列堆积就会延迟。  
2. 方案  
   - **强一致**：使用全局分布式数据库（TiDB/CockroachDB）或 Paxos/Raft 多副本同步写。  
   - **弱一致**：读本地优先，若未命中做跨区同步补偿：客户端先查本地、再读主区（带超时回退）；  
   - **可接受延迟**：在写接口返回时带一个“同步状态”字段，客户端可根据状态决定是否提示“稍后可见”。

## 问题 22：离线修改冲突率特别高

**场景：**  
桌面客户端支持离线编辑文件夹/文件，结果线上调查发现 30% 的同步任务因为冲突需要用户手动解决，体验太差。

**问：**  
1. 为什么冲突这么频繁？  
2. 怎么从协议和实现层面降低冲突率？  

**参考答案：**  
1. 原因  
   - 客户端离线期间多端对同一目录做并行重命名、移动、删除等操作；  
   - 同步机制只按文件级多版本，不做细粒度操作合并。  
2. 优化  
   - 改用 Operation‐based 同步：把文件操作（rename/move/write）序列化成 OP Log；  
   - 采用 CRDT（如 Yjs、Automerge）对目录结构做无冲突合并；  
   - 冲突检测时引入**优先级**（ 最后修改时间＋来源端 ID）自动合并重命名/移动，只对实际内容冲突才人工介入。

## 问题 23：分布式存储数据损坏

**场景：**  
运维发现某个文件在下载后校验失败（MD5 不匹配），偶尔能重试成功，但有个别块始终坏。

**问：**  
1. 可能的原因有哪些？  
2. 如何设计端到端的数据完整性检测与自愈机制？  

**参考答案：**  
1. 可能原因  
   - 存储层（Ceph/S3）硬盘或网络抖动导致写入不完整；  
   - 中间缓存/代理误写或并发写冲突；  
   - SQLite 断点续传元数据读错导致下发了重复或错序的数据块。  
2. 完整性与自愈  
   - **分块校验**：上传/下载时，对每块维护 SHA-256 校验，马上校验失败即重试；  
   - **版本化存储**：对象存储开启多版本；出现损坏时自动回滚到上一版；  
   - **后台巡检**：定时扫描所有块 HASH，对比保存的哈希索引，异步修复（从健康副本或备份拉取）；  
   - **端到端一致性**：完成下载后客户端校验整体文件哈希，不通过则重新发起下载。

## 问题 24：第三方库突发严重漏洞

**场景：**  
FFmpeg 某个版本被曝出严重安全漏洞，需要在 24 小时内完成全量替换并验证新版本兼容性。

**问：**  
1. 紧急响应流程？  
2. 如何在不中断用户服务的前提下完成更新？  

**参考答案：**  
1. 响应流程  
   - 紧急评估影响范围（所有使用该版本的服务/客户端组件）；  
   - 在内部安全通告 + Change Management 系统立刻立案；  
   - 制作修复分支并与 QA 并行测试，确认无重大兼容问题后发布。  
2. 无停机更新  
   - 服务端：用蓝绿部署或 Rolling Update——先升级一小部分节点，跑 smoke test，没有问题再扩容；  
   - 客户端：推送补丁版安装包，利用自带的自动升级机制逐步灰度分发；  
   - 建立回滚方案，一旦出现回归问题，迅速 revert 并切回旧集群/老客户端。
