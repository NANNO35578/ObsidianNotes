# 如何实现视频播放的跳转？

跳转操作可以直接使用 FFMPEG 的跳转函数 `av_seek_frame` 来实现

```c title:"函数原型"
/**
 * Seek to the keyframe at timestamp.
 * 'timestamp' in 'stream_index'.
 *
 * @param s            media file handle
 * @param stream_index If stream_index is (-1), a default stream is selected,
 *                     and timestamp is automatically converted from
 *                     AV_TIME_BASE units to the stream specific time_base.
 * @param timestamp    Timestamp in AVStream.time_base units or, if no stream
 *                     is specified, in AV_TIME_BASE units.
 * @param flags        flags which select direction and seeking mode
 *
 * @return >= 0 on success
 */
int av_seek_frame(AVFormatContext *s, int stream_index, int64_t timestamp, int flags);
```

*参 数*:
- <code>AVFormatContext *s</code> 打开的媒体文件上下文（由 `avformat_open_input` 返回）
- <code>int stream_index</code> 指定流的索引，若为 -1 ，则表示自动选择一个默认流（通常是主视频流）
- <code>int64_t timestamp</code> 目标时间戳，单位是`AVStream.time_base`（即对应流的时间基）
- <code>int flags</code> 控制定位行为的标志位，常用的有以下几种：
	- `AVSEEK_FLAG_BACKWARD` 定位到小于或等于timestamp 的关键帧(I帧)
	- `AVSEEK_FLAG_ANY` 可以定位到任意帧（不一定是关键帧）
	- `AVSEEK_FLAG_FRAME` timestamp 以“帧数”为单位，而不是以时间戳为单位
	- `AVSEEK_FLAG_BYTE` timestamp 以字节为单位, 效率较低

不能直接简单的将当前帧开始放入音、视频队列中进行处理，因为音视频队列中还有之前的的数据，这些数据还可以播放几秒，因此*首先需要清理队列*中这些数据. 若直接放入，会导致跳转时的花屏现象

解决方案：往队列中放入一个特殊的 packet `#define FLUSH_DATA "FLUSH"` ，当解码线程取到这个 packet 的时候，就执行清除解码器的数据

# 如何实现音频, 视频同步?

实际实现音视频同步是以 *音频时钟作为主时钟*

每次解码音频的时候, 都计算音频时钟，每一次解码视频前, 都获取一下当前视频对应显示时间 video_clock(pts)
并且有一个同步线程保证 视频的理论显示时间pts 和 实际应该显示的视频实际video_clock 保持一致, 如果发现视频显示时间大于音频的时间, 那么就延时`SDL_Delay(5)` , 通过这种方式, 来让视音频同步. 让视频追赶音频；

#### 问题1：为什么修改为音频时钟作为主时钟？

系统时钟只显示“当前几点”，但不会驱动 声卡和显卡；
- 声卡晶振只能以固定频率震荡，其本身不能丢样本或者变速度，影响因素只有 制造、温度、老化等；但是系统时间会因为电源、矫正等问题，随时改变此时的时间，频率变化不是稳定的；

#### 问题2：为什么不是视频作为主时钟？

因为视频的容易发生*丢帧和重复帧*，变速也没有明显感觉，显示器的刷新频率也是变化的；
而声卡固定采样率时钟，丢/插样本会立刻听到爆音/杂音，因此音频难以被调整，让容易被修改的视频追赶音频最简单；

# PTS DTS 分别是什么？

PTS（Presentation Time Stamp）是显示时间戳；
DTS（Decoding Time Stamp） 是解码时间戳；同步使用的是PTS

#### 为什么需要两个时间戳？

（I帧 P帧 B帧）需要“先解码后显示”，视频里存在双向参考帧（B 帧），即需要参考前后的I帧和P帧

播放器按 DTS 把数据送进解码器，再按 PTS 把解码后的帧送进渲染队列/声卡。

# 项目中视频预览流程

1. 用户双击主窗口控件的文件条目, 若为文件就是执行文件夹跳转, 若为文件
2. 判断是否为视频格式, 若不是, 预留了接口处理.
3. 将视频文件相关信息, 打包为视频预览请求发送到服务器:
	- 文件id, 用户id, 文件所处目录
4. 服务器收到请求后, 查询数据库, 得到文件MD5
5. 再次检查HLS点播目录下是否存在以该MD5命名的文件夹
	- 若不存在, 创建文件夹, 使用FFmpeg转码源文件到该目录生成`.m3u8`文件以及相关的`.ts`文件
6. 网盘服务器获取与客户端通信ip, 拼凑出视频播放的URL, 回复给客户端
7. 客户端获取到URL后, 使用自己实现的播放器进行打开文件播放.

# 三次握手各个状态, 对应`accept`, `connect`等返回情况分析


假设远端为服务器也就是被动连接的一方; 这一端是主动连接的一端;

最开始近端为closed状态
首先远端bind后调用listen开始监听, 也就是Listen状态; 
远端阻塞在accept;

这一段就是连接服务器调用connect, 阻塞在connect; 
应当是内核发送SYN请求建立连接;
这一段进入SYN_SEND状态

然后远端收到SYN后, 发送SYN+ACK回复; 但是accept仍然阻塞;
进入SYN_RECV状态;

这一端收到SYN+ACK回复, 发送有效ACK, 确认远端的SYN; 
进入established状态, 也就是connect返回;

远端收到有效ACK后, 就由SYN_RECV->established状态;
内核将连接放入已完成队列, accept返回

# 四次挥手内核态与用户态

## Linux上对于一个socket连接, 调用了`close()`就立马关闭了连接吗? 之后还能通过recv或者read读取数据吗?


<div style="display: flex; align-items: top;">
	<div style="flex: 1; margin-left: 10px;">
        <p><strong>四次挥手流程</strong></p>
		<p>1. 对于一个连接, 两端都是established状态, 当这一端调用close之后, 也并不是立马进入FIN_WAIT_1状态, 而是当内核将数据包发送之后才进入<strong style="color:#e69875">FIN_WAIT_1</strong>状态, 此时, send/write返回0, 但是仍然可以通过recv/read读取数据. 也就是<strong style="color:#e67e80">半连接</strong>状态<br></p>
		<p>2. 对于远端, 也就是被动关闭的一端, 收到FIN后, 进入<strong style="color:#e69875">CLOSE_WAIT</strong>状态, 此时recv/read返回0, 但是可以发送数据. 但是收到FIN的第一件事是回复对FIN的ACK.</p>
		<p>当这一端收到对FIN的ACK之后, 就进入了<strong style="color:#e69875">FIN_WAIT_2</strong>状态, 此时仍然是<strong style="color:#e67e80">半连接</strong>状态, 可以读数据<br></p>
		<p>3. 接下来就是远端数据处理完了调用close()关闭连接, 此时远端就进入了<strong style="color:#e69875">CLOSE_WAIT</strong>状态, 向这一端发送FIN;<br></p>
		<p>4. 这一端收到FIN后, 回复ACK, 就进入了<strong style="color:#e69875">TIME_WAIT</strong>状态, 也就是不再能读取任何数据了.<br></p>

TCP_CORK 是干什么的
聚集包, uncork时才发送 **TCP_CORK则是Linux系统所独有的**
##### Nagle 算法 
目的: 尽可能让发送大数据包, 避免网络中充斥着许多小数据包
规则:
1. 若包长度达到MSS允许发送
2. 若FIN包允许发送
3. 设置`TCP_NODELY`允许发送
4. 未设置`TCP_CORK`时, 若发送的所有小数据包都被确认, 则允许发送
5. 若都不满足, 但发生超时, 允许发送
Negle算法默认打开. 如果对于一些需要小数据包交互的场景的程序 比如 telnet或ssh这样的交互性比较强的程序 则需要关闭Nagle算法

- 说完了IOCP, 再说说这个L/F线程池, 是使用C++11的相关特性写的, 这个线程池其实是Leader/Follower, 而不是LockFree无锁线程池. 我这个线程池中呢, 主要有三大角色, 分别是领导者Leader, 追随者Follower以及工作者Processor, 它们是如何工作的呢? 首先, 线程池中应当任何时刻都有一个领导者, 以及若干追随者和一些工作者. 当事务到来时, 我们的领导者就接收到相关的数据以及要处理的任务, 然后唤醒一个追随者, 这个追随者将成为继任领导者, 而这个领导者就拿着事务去干活了, 也就是成为了工作者. 当工作者任务完成后, 就再次提升为追随者.  这就是这个模型的大致流程, 对比与生产者消费者模型, 我了解到这个模型的数据在线程间切换更少, 因为领导者拿到数据就开始了工作, 然而消费者拿到数据后, 还要投递到队列中, 消费者才去取得数据.  这个模型我其实是从wiki上看到的, 有关线程池的条目下相关模型介绍中说到生产者消费者是半同步半异步模型, 以及这个L/F模型.
- 但是呢, 这个线程池和创建IOCP时创建的处理线程不共用, 而且不能共用, 因为IOCP的线程是数据完成时, 将数据取走然后投递到线程池由线程池线程工作. 若不这样做, 假设我们IOCP有4个数据处理线程, 当前一个用户的某个任务耗时较长, 此时其他用户也发出了同耗时任务的请求, 若4个线程在数据完成时, 拿着数据去处理任务了, 那再来用户任务时, 就没有线程将完成的数据拿走, 也就不能达到服务器高可用的目的, 因此, 我们拿到数据后, 就直接将数据投递到线程池, 然后IOCP的接收线程就继续下一个循环, 等待处理下一次数据完成.

[^2]: 为什么选择CS而不是BS模式?
	
	首先我们知道BS模式也就是browser/server模式, 而浏览器访问服务器一般就是应用层协议, 比如HTTP~~(FTP)~~, 而CS也就是client/server模式下, 客户端是我们自己实现的应用层协议;

IO多路复用有哪些, select/poll/epoll区别

[^3]: 为什么选择epoll?
	
	首先说一说什么是IO多路复用: 就是单个线程(进程)同时监听处理多个IO事件, 也就是网络连接. 
	
	然后介绍一下select的使用, 在Linux上, select监听的是一个文件描述符数组, 默认长度为1024, 其中还包含标准输入输出和错误文件描述符, 其次, 监听过程是将这个数组从用户空间拷贝到内核空间, 当有事件可处理时, select调用返回, 将数组再次拷贝到用户空间; 同时, 用户空间的程序也还是不知道有哪些描述符能够操作, 还得遍历一遍数组; 很显然, select的监听对于数量很大的时候就会变慢, 存在延迟; 但也并非没有优点, 比如select的监听返回时间是微秒级别的, 同时跨平台有实现;
	
	对于select介绍到这里, 然后就是poll, 与select区别不大, 但是采用的是链表存储与文件描述符相关的结构体, 没有描述符数量的限制, 但是也要在用户空间与内核空间拷贝这个链表, 同样是遍历找到待处理的文件描述符.
	
	但是epoll集成了select和poll的优点, 监听数量不受限制, 同时在内核空间维护一个由文件描述符的监听节点构成的红黑树, 就不用在内核空间与用户空间频繁拷贝, 同时当事件就绪时只返回就绪节点; 也就是不需要遍历整个监听集合了.
