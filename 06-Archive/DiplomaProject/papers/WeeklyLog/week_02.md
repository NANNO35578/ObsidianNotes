## 工作内容概括

在市场需求明确的基础上，本周对各层技术栈进行深度可行性论证。后端重点对比 C++ Drogon 与 Go Gin 在高并发场景下的性能差异，考虑到后续毕业设计对系统性能深度优化的展示需求，最终选定 **Drogon（C++17/20）** 作为服务端框架，以获得更极致的 IO 性能与异步控制能力。

前端选定 **Vue 3 + Vite** 组合，利用 Composition API 与 Pinia 实现清晰的状态管理；Android 端采用 **Kotlin + MVVM + Jetpack Navigation**，为后续 Room 离线数据库与 WorkManager 后台同步预留扩展空间。基础设施层面确认引入 **MariaDB** 作为主数据库、**Elasticsearch 8.12.2 + IK 分词** 承担全文检索、**MinIO** 作为对象存储、**DeepSeek API** 提供 AI 标签生成能力。

## 详细工作记录

### 一、后端框架选型深度对比

本周投入最多精力的环节是后端技术栈的最终拍板。候选方案有三组：

| 方案 | 框架 | 语言 | 预估 QPS（单核） | 开发效率 | 生态成熟度 | 部署复杂度 |
|------|------|------|------------------|----------|------------|------------|
| A | Drogon | C++17/20 | 80k+（官方 benchmark） | ⭐⭐ | ⭐⭐⭐ | 中 |
| B | Gin | Go 1.21+ | 50k+ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 低 |
| C | Spring Boot 3 | Java 17 | 20k+ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 低 |

#### 1.1 性能压测验证

为验证 Drogon 的实际表现，在实验室服务器（Intel i7-12700, 32GB RAM, Ubuntu 22.04）上搭建了最小 HTTP 服务对比：

```bash
# Drogon 最小服务（返回 JSON {"hello":"world"}）
wrk -t12 -c400 -d30s http://localhost:8888/api/test
# 结果：Requests/sec: 82,341，Latency: 4.82ms（P99: 12ms）

# Gin 最小服务
wrk -t12 -c400 -d30s http://localhost:8080/api/test
# 结果：Requests/sec: 54,127，Latency: 7.34ms（P99: 18ms）
```

Drogon 在纯 HTTP 吞吐量上领先约 52%，且内存占用更低（常驻内存约 12MB vs Gin 的 28MB）。但更复杂的场景（含数据库查询）中，差距缩小至 20-30%，因为瓶颈转移至 MariaDB 连接池。

#### 1.2 开发效率风险评估

C++ 的开发效率劣势不容忽视。实验室内部讨论时，有同学提出「用 Go 三周能做完的 API，C++ 可能要五周」。为降低风险，制定了以下补偿策略：

- **ORM 自动化**：Drogon 自带 `drogon_ctl create model`，可自动生成数据库 Model 类，杜绝手写 SQL 拼接；
- **Service 层模板化**：Controller 与 Service 的代码结构高度统一，新增模块可复制模板快速填充；
- **不追求过度优化**：仅在 IO 密集场景（文件上传、ES 同步）使用异步，常规 CRUD 允许同步写法以降低心智负担。

最终决策：采用 **Drogon**。理由不仅是性能数字，更重要的是毕业设计需要展示「从系统架构到性能调优的完整技术深度」，C++ 后端在答辩中更具区分度。

### 二、前端框架选型

Vue 3 与 React 18 的对比相对快速，重点考察以下维度：

| 维度 | Vue 3 + Vite | React 18 + Vite |
|------|--------------|-----------------|
| 学习曲线 | 平缓（模板语法直观） | 陡峭（JSX + Hooks 规则多） |
| Markdown 编辑器生态 | md-editor-v3（成熟，中文社区活跃） | react-markdown-editor-lite（较旧） |
| 状态管理 | Pinia（简洁，TypeScript 友好） | Redux Toolkit / Zustand |
| UI 组件库 | Element Plus（企业级，文档完善） | Ant Design（同等成熟） |
| 主题切换实现 | CSS 变量 + 组合式函数，极轻量 | CSS-in-JS 或 Tailwind，略重 |

**决策**：Vue 3。核心理由是 md-editor-v3 对中文 Markdown 编辑的支持远优于 React 生态同类产品，且 Element Plus 的 `ElSplitter` 三栏布局组件可直接复用，减少自研成本。

### 三、基础设施选型确认

#### 3.1 数据库：MariaDB vs PostgreSQL

PostgreSQL 在功能丰富度上占优（JSONB、CTE、窗口函数），但 Drogon ORM 对 MySQL/MariaDB 的支持更成熟，且实验室已有 MariaDB 运维经验。最终选定 **MariaDB 10.11**，字符集 `utf8mb4`。

#### 3.2 搜索引擎：Elasticsearch vs Meilisearch

Meilisearch 轻量易部署，但中文分词支持弱于 ES + IK 组合。考虑到推荐系统需要复杂的聚合查询（热门标签、用户行为统计），ES 的 DSL 表达能力更强。**Elasticsearch 8.12.2 + IK 分词器** 入选。

#### 3.3 对象存储：MinIO vs 本地磁盘

本地磁盘方案在毕业设计场景下最简单，但无法模拟真实生产环境的文件上传链路（预签名 URL、异步状态追踪、公开访问控制）。MinIO 作为 S3 兼容的轻量级对象存储，Docker 一键部署，**MinIO** 入选。

#### 3.4 AI 服务：DeepSeek vs Kimi vs 本地 LLM

| 方案 | 成本 | 延迟 | 准确率 | 部署复杂度 |
|------|------|------|--------|------------|
| DeepSeek API | 低（约 ¥0.003/1K tokens） | 中（1-3s） | 高 | 极低 |
| Kimi API | 中（约 ¥0.012/1K tokens） | 高（3-5s） | 高 | 极低 |
| 本地 Qwen-7B | 无（GPU 已具备） | 低（本地推理） | 中 | 高 |

**决策**：优先集成 DeepSeek API（成本低、延迟可接受），同时预留 `KimiService` / `DsService` 的抽象接口，方便后续切换或降级至本地模型。

### 六、风险登记与应对

| 风险项 | 可能性 | 影响 | 应对策略 |
|--------|--------|------|----------|
| Drogon ORM 不支持某复杂查询 | 中 | 高 | 预留原生 SQL 执行路径（`execSqlAsync`） |
| DeepSeek API 稳定性不足 | 中 | 中 | 封装抽象 Service 层，可切换至 Kimi 或本地模型 |
| ES 索引与 DB 数据不一致 | 高 | 中 | 采用「DB 为主、ES 异步补偿」策略，允许短期不一致 |
| Android Room 与后端模型差异 | 中 | 低 | 统一 JSON 契约，Room Entity 与 Response 分离 |
| 毕业设计时间超预期 | 低 | 高 | 每两周与导师同步进度，预留 2 周缓冲 |
