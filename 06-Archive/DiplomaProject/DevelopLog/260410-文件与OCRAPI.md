# 修改



请仔细阅读以下 C++ 异步代码段错误问题分析与修复要求，**严格按照要求修改代码**。

## 一、问题定位

1. **崩溃现象**
    程序运行出现`SIGSEGV`段错误，崩溃栈指向`std::string::clear()`，实际为**悬空指针野访问**。
2. **核心错误原因**
	- 上层OcrController.cc中271行调用`MinioClient::uploadFile`时，仅传递`std::shared_ptr<std::vector<uint8_t>>`的 ** 原始裸指针`data()`** 与`size()`；
	- 函数内部将该裸指针捕获到`queueInLoop`异步任务与子线程中使用；
	- 异步线程执行时，外层`shared_ptr`已被释放，对应内存被销毁，裸指针变为**悬空指针**，子线程访问导致段错误；
	- 本质是**跨线程异步场景下，仅传递裸指针未托管内存生命周期**。
3. **错误代码位置**
	- `OcrController::processOcrWorkflow`中调用`uploadFile`处，271行. 传参为`fileData->data()`、`fileData->size()`；
	- `MinioClient::uploadFile`函数签名接收`const uint8_t* data, size_t dataSize`，并在异步 lambda 中捕获该悬空指针。

## 二、严格修改要求

1. **修改`MinioClient::uploadFile`函数签名**
    - 移除`const uint8_t* data, size_t dataSize`参数；
    - 新增参数`std::shared_ptr<std::vector<uint8_t>> fileData`，直接托管内存。
    
2. **修改`uploadFile`函数内部实现**
    - 异步 lambda 中捕获`fileData`，通过`fileData->data()`、`fileData->size()`安全获取指针与长度；
    - 保留原有`dataCopy`拷贝逻辑与 CURL 上传逻辑，业务代码完全不变。
    
3. **修改上层调用处`OcrController::processOcrWorkflow`**
    - 调用`uploadFile`时，直接传递`fileData`智能指针，不再传递裸指针与长度；
    - 回调捕获逻辑、日志、业务流程保持完全一致。
    
4. **约束条件**
    - 不修改任何业务逻辑、日志输出、接口返回值；
    - 不新增类、全局变量、第三方依赖；
    - 保证线程安全，延长内存生命周期至异步线程执行完毕；
    - 代码风格、命名规范与原代码保持统一。

### 修复核心思路

**问题**: 裸指针 `data()` 被捕获到异步线程中，但外层的 `shared_ptr` 已释放，导致悬空指针访问。

**解决**: 直接传递 `std::shared_ptr<std::vector<uint8_t>>` 智能指针到异步 lambda 中，利用引用计数机制延长内存生命周期，确保异步线程执行期间内存始终有效。

### 关键代码变更

```cpp
// 异步 lambda 捕获智能指针，延长内存生命周期
drogon::app().getLoop()->queueInLoop([this, objectKey, fileData, contentType, callback]() {
    // 安全访问数据，fileData 智能指针保证内存有效
    std::vector<uint8_t> dataCopy(fileData->data(), fileData->data() + fileData->size());
    // ... 后续 CURL 上传逻辑保持不变
});
```
