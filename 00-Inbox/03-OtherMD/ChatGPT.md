# 五、我建议你把“状态机”拆成三层理解

很多大型 C 项目的状态机看起来很复杂，但实际上可以分成三层。

## 第一层：状态是什么？

比如：

```text
IDLE
  │
  ▼
ESTABLISHING
  │
  ▼
ESTABLISHED
  │
  ▼
RELEASING
  │
  ▼
IDLE
```

这只是业务生命周期。

---

## 第二层：什么事件触发状态变化？

例如：

```text
当前状态：IDLE
收到事件：PDU_SESSION_ESTABLISH_REQUEST
                 │
                 ▼
          ESTABLISHING
```

或者：

```text
当前状态：ESTABLISHING
收到事件：SMF_SESSION_ESTABLISH_SUCCESS
                 │
                 ▼
          ESTABLISHED
```

你真正要找的是：

```text
State + Event
        │
        ▼
      Action
        │
        ▼
   Next State
```

可以抽象成：

```text
┌────────────┐
│ Current    │
│ State      │
└─────┬──────┘
      │
      │ Event
      ▼
┌────────────┐
│ Handler    │
│ Action     │
└─────┬──────┘
      │
      ▼
┌────────────┐
│ Next State │
└────────────┘
```

---

## 第三层：状态机实际做了什么？

例如：

```text
IDLE
  │
  │ Create Session
  ▼
ESTABLISHING
  │
  ├──► 请求 RFC 获取策略
  │
  ├──► 请求 URM 分配资源
  │
  ├──► 请求 SM 创建会话
  │
  └──► 请求 TRM 创建用户面资源
                  │
                  ▼
             ESTABLISHED
```

这才是你汇报真正有价值的地方。

**不要只展示“状态A跳到状态B”。**

要展示：

> **为什么跳？由什么事件触发？中间调用了谁？成功/失败后去哪？**
