# IO复用模型--`poll`模型 : 

- 与`select`模型相似
- 可以用poll的监听数组,存储所有客户端socket
- poll模型允许用户自定义长度数组,作为监听集合,每个元素都是 `struct pollfd node`
	`struct pollfd listen_array[100000];//自定义长度`
##### `struct pollfd node;` 结构体:
```c
	node.fd = sockfd; //存储监听的socket,取消监听设置-1
	node.events = POLLIN| POLLOUT| POLLERR; //设置要监听的socket事件
	(node.revents == POLLIN) //当socket就绪后,传出就绪事件,后续使用revents判断socket就绪
```
##### `poll` 函数:
```c
int ready = poll(listen_array, int nfds,int timeout); 
	timeout(-1阻塞) (>0定时阻塞ms) (0非阻塞)
	poll默认阻塞监听,监听到就绪后返回就绪的数量,用户处理就绪即可
```

> [!abstract] `poll` 文件描述符超过1024
> 1. 使用`ulilmit -n x`命令将当前终端程序以及子程序最大文件描述符*暂时修改*为 x
> 2. 修改`/etc/security/limit.conf`文件将`nofile` 选项设置 重启
> 3. 对于WSL 方法2不生效 在`~/.bashrc`中添加方法1 命令

##### 模型利弊
- *优点*
1. poll可以监听的事件数量更丰富
2. poll可以对不同的socket进行不同的监听设置,设置方式更灵活
3. 进行了传入传出分离设置,event传入监听的事件,revents传出就绪事件
- *弊端*
1. 轮询问题,随着轮询数量的增长,IO处理性能呈线性下降
2. poll只返回就绪的数量,没有反馈就绪的socket,需要用户自行遍历查找,开销较大
3. poll多轮使用会出现大量重复的拷贝开销和挂载监听开销

# IO复用模型--`epoll`模型 : 
- 底层红黑树存储

`int epfd = epoll_create(int maxNode);` 创建红黑树，成功返回描述符，失败-1
##### `epoll_ctl();` 函数
`epoll_ctl(int epfd, EPOLL_CTL_ADD, int sockfd, struct epoll_events* node);`
	- 参数1 `int` 为待修改的树
	- 参数2 操作方式`EPOLL_CTL_ADD | EPOLL_CTL_DEL | EPOLL_CTL_MOD`
	- 参数3 `int` 索引
	- 参数4 `struct epoll_event *` 节点
- 修改不可修改节点`data.fd` 因其作为索引 只可修改监听的事件
- *自带互斥锁* 多线程对树访问 无需担心线程安全问题

##### `struct epoll_event node` 结构体
```c
	node.data.fd; // 存储socket节点
	node.events; // 监听的事件  
	node.epoll_item_callback; // 回调函数
```

##### `epoll_wait()` 函数
`int readys = epoll_wait(int epfd, struct epoll_events * ready_arr, int rfds, int timeout);`
	参数1 监听树描述符
	参数2 就绪队列 传出的readys个就绪的节点
	参数3 最大就绪数(监听数)
	参数4 `timeout(-1阻塞) (>0定时阻塞ms) (0非阻塞)`

## 优化点
- **一树一链表一队列**
![['attachments/epoll底层.png]]


1. 避免重复拷贝 : 监听集合(红黑树)定义到内核中
2. 避免轮询 : 不借用io设备等待队列，直接借用网卡监听. 工作时将当前节点抽象为监听项`epitem`，将监听项传给网络设备(网卡)~~绑定~~，网络设备监听
3. epoll有强大监听能力,而且没有额外开销,理论上可以监听系统最大描述符数量
4. epoll监听到就绪直接传出就绪的socket到用户层,用户直接处理即可
5. epoll有丰富的监听事件,设置监听的灵活性更好

* Epoll较为适合,高并发低活跃场景
* select适用于低监听量,高括跃的场景
