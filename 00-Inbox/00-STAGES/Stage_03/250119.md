|                                                                                                                                                                                                                                                         |                  |

| 0).开始 客户端和服务端都处于CLOSE状态 服务端主动监听某个端口 处于LISTEN状态<br>1).客户端主动发起连接 SYN 之后处于 SYN-SEND 状态<br>2).服务端收到发起的连接 返回 SYN 并且 ACK客户端的 SYN 之后处于SYN-RCVD 状态<br>3).客户端收到服务端发送的 SYN和ACK之后 发送ACK的ACK 之后处于ESTABLISHED(可用)状态 一发一收成功<br>4)服务端收到ACK的ACK之后 处于STABLISHED状态 同样一发一收 | ![[TCP三次握手.png]] |

2. 为什么是三次不是四次(SYN和ACK不分开发) : SYN与ACK一起发 因为两标志位逻辑上互不影响工作 同时逻辑不冲突 _为什么不是两次(1.2包) :_ 两次时 服务端当客户端发送请求建立连接SYN 回复确认后 就可以发送数据 _但若客户端在发送SYN后关闭_ 服务器将无法识别 
# TCP 四次挥手断开连接

_2MSL_ : $2*maximum*segment*lifetime$ 2倍报文段最大存活时间


为什么不是三次

|                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1)主动方打算关闭连接 发送一个TCP首部 FIN标志位被置为1的报文 也即FIN报文 主动方进入 `FIN_WAIT_1`状态<br><br>2)被动方收到该报文后 就向主动方发送 ACK应答报文(可能包含剩余数据) 接着被动方进入`CLOSED_WAIT`状态<br><br>3)主动方收到被动方的ACK应答报文后 之后进入`FIN_WAIT_2`状态<br><br>4)等待被动方处理完数据后 也向主动方发送FIN报文 之后被动方进入`LAST_ACK`状态<br><br>5)主动方收到被动方的FIN报文后 回一个ACK应答报文 之后进入 `TIME_WAIT`状态<br><br>6)被动方收到了ACK应答报文后 就进入了`CLOSED`状态 至此被动方已经完成连接的关闭<br><br>7)主动方在经过 _2MSL_ 一段时间后 自动进入`CLOSED`状态至此主动方也完成连接的关闭<br> |
| ![[TCP四次挥手.png]]                                                                                                                                                                                                                                                                                                                                                                                                   |
_考点_ :
1. TCP四次挥手流程
2. 为什么最后等待 _2MSL_ : 保证最后一个ACK发送到对端 若丢了会触发超时重传 重新等待
3. 为什么是四次不是三次(2.3合并) : FIN表示不再发送有效数据 被动断开连接端可能剩余数据未处理 不能发送FIN报文(表示无有效数据了) 同时为了防止请求方超时重传 需立马回复但不能发送FIN

# RTT(Round-Trip Time)
> 往返时延 ~~ping~~
- 在计算机网络中它是一个重要的性能指标,表示从发送端发送数据开始,到发送端收到来自接收端的确认(接收端收到数据后便立即发送确认),总共经历的时延。

- RTT由三个部分决定:即 _链路的传播时间_ _末端系统的处理时间_ 以及 _路由器的缓存中的排队和处理时间_。
# RTO(Retransmission Timeout)
> 超时重传时间

- TCP每发送一个报文段,就对此报文段设置一个超时重传计时器。此计时器设置的超时重传时间RTO应当略大于TCP报文段的平均往返时延RTT,一般可取RTO=2RTT。

- 但是,也可以根据具体情况人为调整RTO的值,例如可以设置此超时重传时间RTO=90秒。当超过了规定的超时重传时间还未收到对此TCP报文段的预期确认信息,则必须重新传输此TCP报文段。

# TCP流量控制-滑动窗口
- _窗口概念_:TCP是每发送一个数据 都要进行一次确认应答 当上一个数据包收到了应答了 再发送下一个 _缺点_:效率比较低
- 有了窗口 就可以指定窗口大小 窗口大小就是指无需等待确认应答 而可以继续发送数据的最大值

> _窗口大小由哪一方决定?_
> 三次握手的时候 会交换窗口大小 通常窗口的大小是由接收方的窗口大小来决定的。发送方发送的数据大小不能超过接收方的窗口大小 否则接收方就无法正常接收到数据。

# 粘包问题
- _原因_ : TCP是基于字节流的 是一种没有边界的 可以合并的传输方式
- 
多组数据存储到发送/接收缓冲区 

==解决方法== : 
1. 设置标志位 : 起始/结束标志位 缺点 : 数据可能会与标志重复 起始标志还可能会导致无法确定何处结束 (考虑数据类型是否固定)
2. 固定包大小 : 缺点 可能浪费空间 (适用于大文件自行拆包情况)
3. 先发数据长度 再发数据内容 : 缺点 多发一个包
4. 短连接 : 建立连接时发送数据然后断开 适用于用户操作间隔时间长
