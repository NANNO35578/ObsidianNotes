# 第五章：实时通信架构

## 5.1 架构概述

实时通信系统的架构决定了系统的性能、可扩展性和成本。不同的架构适用于不同的场景。

## 5.2 P2P架构

### 5.2.1 架构特点

**P2P（Peer-to-Peer）** 架构是点对点直连架构。

```
客户端A ←→ 客户端B
```

#### 优势
- **低延迟**：直接连接，延迟最低
- **低成本**：不需要服务器转发，节省带宽和服务器成本
- **简单**：架构简单，易于实现

#### 劣势
- **NAT穿透问题**：需要STUN/TURN服务器
- **可扩展性差**：多人场景下，每个客户端需要向所有其他客户端发送数据
- **带宽消耗**：每个客户端需要上传多份数据

### 5.2.2 适用场景

- **一对一通话**：最适合P2P架构
- **小规模会议**：2-4人
- **低延迟要求**：对延迟要求极高的场景

### 5.2.3 带宽计算

对于N人会议：
- **每个客户端上传**：N-1 路
- **每个客户端下载**：N-1 路
- **总带宽**：N × (N-1) × 单路带宽

例如：4人会议，每路1Mbps
- 每个客户端上传：3 Mbps
- 每个客户端下载：3 Mbps
- 总带宽：12 Mbps

## 5.3 SFU架构

### 5.3.1 架构特点

**SFU（Selective Forwarding Unit）**是选择性转发单元架构。

```
客户端A ──┐
客户端B ──┤
客户端C ──┼── SFU服务器 ──→ 客户端A
客户端D ──┘              ├──→ 客户端B
                         ├──→ 客户端C
                         └──→ 客户端D
```

#### 工作原理
1. 每个客户端只向SFU服务器上传一路流
2. SFU服务器接收所有流
3. SFU服务器根据需求选择性转发给其他客户端

#### 优势
- **可扩展性好**：支持大规模会议（几十到几百人）
- **带宽效率**：每个客户端只需上传一路
- **灵活控制**：服务器可以控制转发策略
- **低延迟**：相比MCU延迟更低

#### 劣势
- **服务器成本**：需要服务器转发
- **带宽成本**：服务器需要大量带宽
- **复杂度**：需要实现转发逻辑

### 5.3.2 转发策略

#### 全部转发（Full Mesh）
- 每个客户端接收所有其他客户端的流
- 适合小规模会议

#### 选择性转发（Selective）
- 只转发活跃发言人的流
- 只转发视频流，不转发音频流（节省带宽）
- 根据网络状况选择转发质量

#### 订阅模式（Subscribe）
- 客户端主动订阅需要的流
- 更灵活，节省带宽

### 5.3.3 适用场景

- **多人会议**：4-100人
- **直播连麦**：主播和连麦用户
- **在线教育**：老师和学生
- **远程协作**：团队协作

### 5.3.4 带宽计算

对于N人会议：
- **每个客户端上传**：1 路
- **每个客户端下载**：N-1 路（全部转发）
- **服务器总带宽**：N × (N-1) × 单路带宽

例如：10人会议，每路1Mbps
- 每个客户端上传：1 Mbps
- 每个客户端下载：9 Mbps
- 服务器总带宽：90 Mbps

## 5.4 MCU架构

### 5.4.1 架构特点

**MCU（Multipoint Control Unit）**是多点控制单元架构。

```
客户端A ──┐
客户端B ──┤
客户端C ──┼──→ MCU服务器（混流） ──→ 客户端A
客户端D ──┘              ├──→ 客户端B
                         ├──→ 客户端C
                         └──→ 客户端D
```

#### 工作原理
1. 每个客户端向MCU服务器上传流
2. MCU服务器解码所有流
3. MCU服务器将多路流混合成一路（混流）
4. MCU服务器编码并发送给所有客户端

#### 优势
- **带宽效率最高**：每个客户端只需下载一路
- **兼容性好**：可以处理不同编码格式
- **质量控制**：服务器可以统一控制质量
- **布局控制**：可以控制视频布局（画中画、分屏等）

#### 劣势
- **延迟高**：需要解码、混流、编码，延迟增加
- **服务器成本高**：需要强大的计算能力
- **复杂度高**：需要实现混流逻辑
- **可扩展性差**：受服务器性能限制

### 5.4.2 混流方式

#### 视频混流
- **画中画（PIP）**：主画面+小窗口
- **分屏**：多路视频并排显示
- **智能布局**：根据活跃度调整布局

#### 音频混流
- **混音**：将多路音频混合
- **选择**：只转发主要发言人的音频

### 5.4.3 适用场景

- **大规模会议**：100+人
- **直播场景**：需要统一画面的场景
- **低带宽环境**：客户端带宽有限
- **兼容性要求**：需要支持多种编码格式

### 5.4.4 带宽计算

对于N人会议：
- **每个客户端上传**：1 路
- **每个客户端下载**：1 路（混流后）
- **服务器总带宽**：N × 单路带宽（上传）+ N × 单路带宽（下载）

例如：10人会议，每路1Mbps
- 每个客户端上传：1 Mbps
- 每个客户端下载：1 Mbps
- 服务器总带宽：20 Mbps

## 5.5 混合架构

### 5.5.1 架构特点

结合P2P、SFU、MCU的优势，根据场景动态选择。

#### 策略
- **小规模（2-4人）**：使用P2P
- **中规模（5-20人）**：使用SFU
- **大规模（20+人）**：使用MCU或SFU+MCU混合

### 5.5.2 智能切换

根据以下因素动态切换：
- **参与人数**
- **网络状况**
- **设备性能**
- **业务需求**

## 5.6 架构对比

| 架构 | 延迟 | 带宽效率 | 可扩展性 | 服务器成本 | 适用场景 |
|------|------|---------|---------|-----------|---------|
| P2P | 最低 | 低 | 差 | 低 | 1对1，小规模 |
| SFU | 低 | 中 | 好 | 中 | 多人会议 |
| MCU | 高 | 高 | 中 | 高 | 大规模，低带宽 |
| 混合 | 可变 | 可变 | 好 | 中高 | 复杂场景 |

## 5.7 信令服务器

### 5.7.1 作用

信令服务器负责：
1. **用户管理**：用户注册、登录、状态管理
2. **房间管理**：创建房间、加入房间、离开房间
3. **信令交换**：SDP交换、ICE候选交换
4. **权限控制**：权限管理、访问控制

### 5.7.2 协议选择

#### WebSocket
- **优势**：双向通信、实时性好、浏览器支持
- **适用**：Web应用

#### SIP
- **优势**：标准协议、兼容性好
- **适用**：传统电话系统、企业通信

#### 自定义协议
- **优势**：灵活、高效
- **适用**：特定场景

### 5.7.3 信令流程

```
客户端A                   信令服务器                   客户端B
   |                           |                           |
   |---- 创建房间 ------------>|                           |
   |<--- 房间ID  --------------|                           |
   |                           |                           |
   |---- 加入房间 ------------>|                           |
   |                           |<---- 加入房间 ------------|
   |                           |---- 通知A有用户加入 ----->|
   |                           |<---- SDP Offer  ----------|
   |<---- SDP Offer -----------|                           |
   |---- SDP Answer ---------->|                           |
   |                           |---- SDP Answer ---------->|
   |                           |<---- ICE Candidate -------|
   |<---- ICE Candidate -------|                           |
   |---- ICE Candidate ------->|                           |
   |                           |---- ICE Candidate ------->|
```

## 5.8 架构设计原则

### 5.8.1 可扩展性

- **水平扩展**：支持多服务器部署
- **负载均衡**：合理分配负载
- **动态扩容**：根据负载自动扩容

### 5.8.2 高可用性

- **冗余设计**：多服务器备份
- **故障转移**：自动故障恢复
- **监控告警**：实时监控系统状态

### 5.8.3 性能优化

- **就近接入**：CDN加速
- **智能路由**：选择最优路径
- **缓存优化**：减少重复计算

## 5.9 实践建议

1. **根据场景选择架构**：不同场景适合不同架构
2. **考虑成本**：服务器成本和带宽成本
3. **预留扩展空间**：考虑未来扩展需求
4. **监控和优化**：持续监控和优化系统
