## 什么是索引

索引相当于字典的目录, 帮助快速查找到*众多数据*中的一个(或多个). *索引就是用来帮助表快速检索目标数据的*.

数据库基于磁盘工作, 所有数据会放在磁盘上存储, 同样, 索引也是数据像表一样存储在磁盘上, 生成本地文件.
*何种方式*存储: 由索引数据结构决定, 最终由存储引擎决定, 因此, 不同存储引擎下的索引文件, 保存在本地的格式也不相同

# 索引创建 查询 删除
创建索引

```sql title:"创建索引"
-- 方式 Ⅰ
CREATE UNIQUE INDEX indexName ON tableName (columnName(length));

-- 方式 Ⅱ
ALTER TABLE tableName ADD UNIQUE INDEX indexName(columnName);

-- 方式 Ⅲ
CREATE TABLE tableName(  
  columnName1 INT(8) NOT NULL,   
  columnName2 ....,
  .....,
  UNIQUE INDEX [indexName] (columnName(length))  
);
```
- 创建主键索引, 必须先将索引字段设置为主键. 不能使用`CREATE` 而是使用`ALTER`. 关键字不能使用`INDEX`而是使用`KEY`
- *全文索引*创建: MySQL after 5.7(before use MyISAM) . INDEX前添加FULLTEXT关键字. 字段为文本类型. 若要支持中文使用`{sql}With Parser ngram`

##### 查询索引
- 索引创建完成后，可通过`{sql}SHOW INDEX FROM tableName;`这条命令查询一个表中拥有的索引

##### 删除索引
- 建错了索引，只能先删再重新建立一次`{sql}DROP INDEX indexName ON tableName;`

##### 指定索引查询
- 强制性的为`SELECT`语句指定索引，如下：`{sql}SELECT * FROM table_name FORCE INDEX(index_name) WHERE .....;`
- `FORCE INDEX`关键字可以为一条查询语句强制指定走哪个索引查询，但要牢记的是：**如果当前的查询**`SQL`**压根不会走指定的索引字段，那这种方式是行不通的**，这个关键字的用法是：一条查询语句在*有多个索引可以检索数据时*，显式指定一个索引，减少优化器选择索引的耗时
如果对于整个业务系统不熟悉的话，还是交给优化器来自行选择，否则会适得其反！

# 索引分类
- 索引有: 聚簇索引, 非聚簇索引; 唯一索引, 主键索引, 联合索引, 全文索引, 单列索引, 多列索引, 复合索引, 普通索引, 二级索引, 辅助索引, 次级索引, 有序索引, $B^+ Tree$索引, $R-Tree$索引, $T-Tree$索引, $Hash$索引, 空间索引, 前缀索引....
其实并没有这么多索引,上述列出的索引称呼中，有几个称呼对应的索引是同一个，有一部分只是逻辑上的索引

## 数据结构层次
MySQL索引支持的数据结构有:
1. $B^+Tree$: 最常用索引结构, 大部分存储引擎支持, 有序.
2. $Hash$: 大部分支持, 字段不重复查询最快, 无序.
3. $R-Tree$: MyISAM引擎支持, *空间索引* 的默认结构类型.
4. $T-Tree$: *NDB-Cluster*引擎支持, 主要用于`MySQL-Cluster`服务中. 
除开列出的几种索引结构外，`MySQL`索引支持的数据结构还有`R+、R*、QR、SS、X`树等结构.

在`MySQL`中创建索引时，其默认的数据结构就为`B+Tree`，如何更换索引的数据结构呢？如下：

```sql
CREATE INDEX indexName ON tableName (columnName(length) [ASC|DESC]) USING HASH;
```

也就是在创建索引时，通过`USING`关键字显示指定索引的数据结构（必须要为当前引擎支持的结构）


## 字段数量层次

从字段数量出发可分为单列索引与多列索引. 单列基于一个字段, 多列基于多个字段组合建立索引
*单列索引*可分为多种:
1. *唯一索引*: 指索引中节点值不允许重复, 一般配合唯一字段约束(unique)使用.
2. *主键索引*: 特殊的唯一索引, 区别在于*不允许有空值*.
3. *普通索引*: 通过KEY,INDEX关键字创建的索引, 没有限制, 单纯使查询快一点
总之: 基于单个字段的索引都可以成为单列索引

*多列索引*还有很多叫法: 组合索引, 联合索引, 复合索引, 多值索引... 即由多个字段建立的索引.
- 值得注意的是, 当`{sql}SELECT`包含多列索引中*第一个字段*时,才能使用多列索引.

> 与此同时在创建索引时, `length`字段代表如果字段存储长度过长, 选用前多少个字符创建索引. *使用一个字段值中前N个字符创建的索引就可以被称为* **前缀索引**. 前缀索引可节省索引文件存储空间, *提升索引性能*

## 存储方式层次

### 聚簇索引
AKA聚集索引, 聚类索引. 一般要求为非空唯一的索引(MySQL默认是主键索引作为). 若无非空唯一的字段, InnoDB隐式定义一个主键
### 非聚簇索引
AKA非聚集索引, 非聚类索引, 二级索引, 辅助索引, 次级索引

##### 主要区别
聚簇索引逻辑上连续时, 物理空间也连续. 非聚簇索引, 逻辑上连续, 物理空间不连续
- 一张表只能存在一个聚簇索引, 可以存在多个非聚簇索引.

# 索引优劣
> [!example] 索引引入的优势
> 1. 整个数据库中, 数据表的查询速度直线上升, 数据量越大越明显.
> 2. 创建*唯一索引*, 就可以确保数据唯一, 无需额外建立*唯一约束*
> 3. *分组和排序*显著减少分组和排序时间.
> 4. 连表查询, 基于主外键建立索引, 可以带来十分明显的性能提生.
> 5. MySQL默认$B^+Tree$为结构的索引, *范围查询*效率提高
> 6. 整体而言, 减少查询SQL的执行时间, 提高数据库*整体吞吐*.

> [!abstract] 引入索引的劣势
> 1. 建立索引会生成本地磁盘文件, 需要额外空间存储
> 2. 写入数据时, 需要额外维护索引结构, 增删改数据, 都要维护索引
> 3. 整体上看, 维护索引会使执行写SQL的效率降低, 性能下降

- 但整体而言, 优势大于劣势

##### 主键索引为什么一般自增? 若为保证不重复的话, UUID也不重复, 为什么不用UUID呢?
- 原因是, 默认情况下的$B^+Tree$是有序的, 聚簇索引中表数据和索引数据存放在一起, 保证有序的情况下. 自增当然没问题, 都是放最后. 
- 可是UUID是无序的, 每当插入一条新数据就有可能破坏原本树的结构.
因此, 主键最好选用顺序性值.

##### 联合索引的矛盾
- 使用联合索引要求第一个字段必须出现. 若第一个字段命中率不高, 联合索引可能用处不大.
- 因此, 建立联合索引时要考虑*索引字段第一个查询命中率要高*

##### 前缀索引弊端
- 因为索引字段未存储一个完整的字段值, 无法使用前缀索引完成`{sql}ORDER BY, GROUP BY`等分组排序工作
- 也无法完成覆盖扫描

##### 全文索引的硬伤
- 全文索引基于分词, 相较于like, 速度快
- 但是基于分词, MySQL会对索引字段进行分词处理, 分词结果也会存储在全文索引中, 因此*全文索引的文件会额外大*.
- 还是因为分词, 当对字段修改后, 分词需要时间, 但是修改后不会立马自动更新, 需要手动写存储过程并调用.
- 全文索引对中文支持不友好, 中文分词存在精准度问题
项目够大, 可以使用`ElasticSearch、Solr、MeiliSearch`等搜索引擎

##### 唯一索引快慢问题
- 当普通索引查询到结果时, 不会立即停止检索, 因为可能存在字段值相同的数据.
- 但是若字段为唯一, 即唯一索引的条件下, 就会立马停下检索, 因为唯一字段数据具有唯一性
同时, 在插入时, 会检索表中是否存在相同字段, 而普通索引就无需关心重复问题.

##### 哈希索引的致命问题
哈希索引查询速度快, 只需进行一次哈希计算. 但是无法基于哈希索引作排序, 分组等工作, 同时无法进行范围查询, 因为哈希索引无序.

> [!abstract] 索引查询时 *回表* 问题. 什么是回表? 
> - 一条SQL查询语句在MySQL内部要经过两次查询才能获取到数据
> - where条件中不是主键索引, 而是辅助索引, 第一次查询走的是辅助索引, 查找到主键索引中的键值, 然后再去主键索引中查询. 
> - 比基于主键索引的查询多了一次, 这就是回表

![例如:select * from user where name = ‘张三’;](回表.png)

实际上, 建立联合索引, 利用*索引覆盖*的特性, 从而避免使用辅助索引, 可以消除回表操作.

#### 建立索引应当遵循的规则 
1. 经常频繁用作查询条件的字段应酌情考虑为其创建索引
2. 表的主外键或连表字段，必须建立索引，因为能很大程度提升连表查询的性能
3. 建立索引的字段，一般值的区分性要足够高，这样才能提高索引的检索效率
4. 建立索引的字段，*值不应该过长*，如果较长的字段要建立索引，可以选择前缀索引
5. 建立联合索引，应当遵循最左前缀原则，将多个字段之间按*优先级*顺序组合
6. 经常根据范围取值、排序、分组的字段应建立索引，因为*索引有序*，能加快排序时间
7. 对于唯一索引，如果确认不会利用该字段排序，那可以将结构改为`Hash`结构
8. 尽量使用*联合索引代替单值索引*，联合索引比多个单值索引查询效率要高


同时应当避免：
1. 值经常会增删改的字段，不合适建立索引，因为每次改变后需维护索引结构
2. 一个字段存在大量的重复值时，不适合建立索引，比如之前举例的性别字段
3. 索引不能参与计算，因此经常带函数查询的字段，并不适合建立索引
4. 一张表中的索引数量并不是越多越好，一般控制在`3`，最多不能超过`5`
5. 建立联合索引时，一定要考虑优先级，查询频率最高的字段应当放首位
6. 当表的数据较少，不应当建立索引，因为数据量不大时，维护索引反而开销更大
7. 索引的字段值无序时，不推荐建立索引，因为会造成页分裂，尤其是主键索引

#### 联合索引的最左匹配原则
+ 尽量使用联合索引代替单值索引，联合索引比多个单值索引查询效率要高

对于这一点是为什么呢？举个例子，比如此时基于`X、Y、Z`字段建立了一个联合索引，实际上也相当于建立了三个索引：`X`、`X、Y`、`X、Y、Z`，因此只要查询中使用了这三组字段，都可以让联合索引生效

但如若查询中这三个字段不以*AND*形式出现，而是单独作为查询条件出现，那单值索引性能会好一些，但三个不同的索引，维护的代价也会高一些

其实联合索引的最左前缀原则，道理很简单的，就是*组成联合索引的多个列，越靠左边优先级越高*，同时也只有`SQL`查询条件中，*包含了最左的字段*，才能使用联合索引，例如：

```sql title:"-- 基于上面的哪个X、Y、Z联合索引"
SELECT * FROM tb WHERE Y = "..." AND Z = "...";
```

上面这条`SQL`就显然并不会使用联合索引，因为不符合最左前缀原则，最左侧的`X`字段未曾被使用. 也正由于`MySQL`在使用联合索引时会遵循最左前缀原则，所以才在前面建立索引的建议中给出了一条： 

+ 建立联合索引时，一定要考虑*优先级*，查询频率最高的字段应当放首位

因为将查询频率越高的字段放首位，就代表着查询时命中索引的几率越大. 同时，`MySQL`的最左前缀原则，在匹配到范围查询时会停止匹配，比如`>、<、between、like`这类范围条件，并不会继续使用联合索引，举个栗子：

```sql
SELECT * FROM tb WHERE X="..." AND Y > "..." AND Z="...";
```

当执行时，虽然上述`SQL`使用到`X、Y、Z`作为查询条件，但由于`Y`字段是`>`范围查询，因此这里只能使用`X`索引，而不能使用`X、Y`或`X、Y、Z`索引

对于一条查询`SQL`是否用到了索引，或者一条查询`SQL`到底用了那个索引，其实可以通过`MySQL`自带的*explain*工具分析

最后再来一个简单的栗子，加深一下对于联合索引的认知：

```sql
select * from user where name = '竹子';
select * from user where name = '竹子' and age = 18;

A. create index index_name on user(name);
   create index index_name on user(age);

B. create index index_name on user(name,age);
```

比如上述这个案例中，显然两条`sql`完全能够利用到第二个创建的联合索引

```sql
select * from user where name = '竹子' and age = 18;
select * from user where  age = 18 and name = '竹子';
```

同时选`B`建立联合索引后，如上两条`SQL`都会利用到上面创建的联合索引，`SQL`是否走索引查询跟`where`后的条件顺序无关，因为`MySQL`优化器会优化，对`SQL`查询条件进行重排序

# 索引失效

**选择建了索引，那一定要利用它，否则还不如干脆别建，既能节省磁盘空间，又能提升写入效率**

如何查看: 以`{sql}EXPLAIN` 加sql语句, 查看type字段:
    1. `all`：表示走了全表查询，未命中索引或索引失效
	2. `system`：表示要查询的表中仅有一条数据
	3. `const`：表示当前`SQL`语句的查询条件中，可以命中索引查询
	4. `range`：表示当前查询操作是查某个区间
	5. `eq_ref`：表示目前在做多表关联查询
	6. `ref`：表示目前使用了普通索引查询
	7. `index`：表示目前`SQL`使用了辅助索引查询


##### 1. `{sql}OR` 作为条件会导致索引失效
##### 2. 以`{sql}like '%AKA%'` 即like加前 *\%* 会导致索引失效.
##### 3. 字符类型不加引号导致索引失效
##### 4. 索引字段参与计算导致索引失效
##### 5. 索引字段被用作函数计算也会失效
##### 6. 违背最左匹配原则 
##### 7. 不同字段值对比, 导致索引失效
##### 8. 反向范围操作导致索引失效: `{sql}NOT IN, NOT LIKE`
 - 同时正向操作`IS NULL`也不会走索引, 反向`IS NOT NULL`也不会走
##### 9. 走索引扫描行数超过30% MySQL默认放弃索引

# 索引覆盖
*当查询所需的字段数据，在联合索引中完全包含*，因此可以直接通过联合索引获取到数据.
- 但如果查询时用`*`，因为联合索引中不具备完整的一行数据，只能再次转向聚簇索引中获取完整的行数据
- 因此到这里大家应该也明白了为什么查询数据时，不能用`*`的原因，这是因为会导致索引覆盖失效，造成回表问题

当然，再来提一点比较有意思的事情，先看`SQL`：

```sql
EXPLAIN SELECT 
    `user_name`,user_sex
FROM 
    `zz_users`
WHERE 
    `password` = "1234" AND `user_sex` = "男";
```

比如上述这条`SQL`，显然是不符合联合索引的最左前缀匹配原则的，但通过`EXPLAIN`分析的结果显示，这条`SQL`竟然使用了索引，这是什么原因呢？也是因为索引覆盖

一句话概述：*就是要查询的列，在使用的索引中已经包含，被所使用的索引覆盖*，这种情况称之为索引覆盖

# 索引下推

after MySQL5.6
*将`Server`层筛选数据的工作，下推到引擎层处理* 

索引下推是`MySQL5.6`版本以后引入的一种优化机制，还是以之前的用户表为例，先来看一条`SQL`语句：
`{sql}SELECT * FROM zz_users WHERE user_name LIKE "竹%" AND user_sex="男";` 

这条`SQL`会使用联合索引吗？答案是会的，但只能部分使用，因为联合索引的每个节点信息大致如下：

```sql
{
    ["熊猫","女","6666"] : 1,
    ["竹子","男","1234"] : 2,
    ["子竹","男","4321"] : 3,
    ["1111","男","4321"] : 4,
    ["竹竹","女","8888"] : 5
}
```

由于前面使用的是模糊查询，但`%`在结尾，因此可以使用`竹`这个字作为条件在联合索引中查询，整个查询过程如下：

1. 利用联合索引中的`user_name`字段找出「竹子、竹竹」两个索引节点
2. 返回索引节点存储的值「`2、5`」给`Server`层，然后去逐一做回表扫描
3. 在`Server`层中根据`user_sex="男"`这个条件逐条判断，最终筛选到「竹子」这条数据

为什么`user_sex="男"`这个条件不在联合索引中处理呢？因为*前面是模糊查询*.
- 所以拼接起来是这样的：`竹x男`，由于这个`x`是未知的，因此无法根据最左前缀原则去匹配数据.
- 最终这里只能使用联合索引中`user_name`字段的一部分，后续的`user_sex="男"`还需要回到`Server`层处理

那什么又叫做*索引下推*呢？也就是将`Server`层筛选数据的工作，下推到引擎层处理

以前面的案例来讲解，`MySQL5.6`加入索引下推机制后，其执行过程是什么样子的呢？

1. 利用联合索引中的`user_name`字段找出「竹子、竹竹」两个索引节点
2. 根据`user_sex="男"`这个条件在索引节点中逐个判断，从而得到「竹子」这个节点
3. 最终将「竹子」这个节点对应的「`2`」返回给`Server`层，然后聚簇索引中回表拿数据

相较于没有索引下推之前，原本需要做「`2、5`」两次回表查询，但在拥有索引下推之后，仅需做「`2`」一次回表查询

索引下推在`MySQL5.6`版本之后是默认开启的，可以通过命令`set optimizer_switch='index_condition_pushdown=off|on';`命令来手动管理

# MRR Multi-Range Read机制
- 针对于辅助索引的回表查询，减少离散`IO`，并且将随机`IO`转换为顺序`IO`，从而提高查询效率
- 以查找成绩不合格的学生信息, 每查一个分段的学生信息, 就可能要到磁盘不同页取数据;
*原理*: `MRR`机制中，对于辅助索引中查询出的`ID`，会将其放到*缓冲区*的`read_rnd_buffer`中，然后等全部的索引检索工作完成后，或者缓冲区中的数据达到`read_rnd_buffer_size`大小时，此时`MySQL`会对缓冲区中的数据排序，从而得到一个有序的`ID`集合：`rest_sort`，最终再根据顺序`IO`去聚簇/主键索引中回表查询数据

# Index Skip Scan 索引跳跃式扫描

比如此时通过`(A、B、C)`三个列建立了一个联合索引，此时有如下一条`SQL`：

`{sql} SELECT * FROM tb_xx WHERE B = xxx AND C = xxx; `

按理来说，这条`SQL`既不符合*最左前缀*原则，也不具备使用*索引覆盖*的条件，因此绝对是不会走联合索引查询的，但思考一个问题，这条`SQL`中都已经使用了联合索引中的两个字段，结果还不能使用索引，这似乎有点亏啊对不？
`MySQL8.x`推出了跳跃扫描机制，但跳跃扫描并不是真正的“跳过了”第一个字段，而是优化器为你重构了`SQL`，比如上述这条`SQL`则会重构成如下情况：

```plain
SELECT * FROM `tb_xx` WHERE B = `xxx` AND C = `xxx`
UNION ALL
SELECT * FROM `tb_xx` WHERE B = `xxx` AND C = `xxx` AND A = "yyy"
......
SELECT * FROM `tb_xx` WHERE B = `xxx` AND C = `xxx` AND A = "zzz";
```

其实也就是`MySQL`优化器会自动对联合索引中的第一个字段的值去重，然后基于去重后的值全部拼接起来查一遍，一句话来概述就是：**虽然你没用第一个字段，但我给你加上去，今天这个联合索引你就得用，不用也得给我用**
- 多表联查时无法触发
- `SQL`条件中有分组操作也无法触发
- `SQL`中用了`DISTINCT`去重也无法触发
- .....
如果联合索引的第一个字段，是*一个值具备唯一性的字段*，那去重一次再拼接，几乎就等价于走一次全表

# `MySQL`为何选择$B^+Tree$ 作为索引数据结构

##### 局部性原理

> 比如因特尔的`MESI`协议中，缓存行的默认大小为`64Bytes`，也就是说在因特尔的`CPU`中，一次性会将“当前操作数据”附近的`64Bytes`数据（2页数据）提前载入进高速缓冲区

MySQL的一次磁盘读取像内存那样, 不仅仅会读取一条表数据, 在InnoDB中, 一次默认读取16KB到内存中.

MySQL一次全盘扫描:
- 利用局部性原理, 将读出的数据与SQL语句条件比较, 若不符合, 放弃这条数据, 并且不会对其二次读取
- 若符合条件, 写入结果集, 继续判断其他数据
- 若非唯一性条件, 会继续看表中是否还有剩余数据

对于大数据, 例如表的数据量为百万级, 单条数据大小为512Byte, 一次磁盘IO也就32条, 一次全盘就要跑三万多次, 若为机械, 磁针在磁道上跑, 就将是很费时的.

因此, 建立索引的原因就在于此, 避免全表扫描, 因为全表扫描开销随表数据量增长而增长.

##### 为什么不用 *二叉搜索树$BST$* binary search tree

- 若索引字段按照顺序增长, 二叉树将会是链表结构. 检索过程和全盘扫描无异.
- 树结构在磁盘中, 各节点数据不连续, 也无法使用局部性原理

##### 为什么不用 *红黑树$RBT$* red black tree

红黑树相较于BST, 有自平衡性, 可根据插入节点数量和节点信息来调整平衡. 但同样不适合:
1. 高度相较于BST有所降低, 但是仍然会很高: 接近$log_2(n)$
2. 每个节点还是只存储一个数据, 仍然无法使用局部性原理


*是不是单个节点存储多个数据就可?*

##### 为什么不用 *$B-Tree$* ?

相较于RBT, 更矮了, 节点数据更多了, 也能用上局部性原理. 但是当使用范围查询时, 小范围几个能接受, 但是*当范围很大时候*, 依旧需要多次磁盘IO

##### 为什么选择 *$B^+Tree$* ?

由于B-Tree不适合作大范围查询, 因此, 在$B^+Tree$的叶子节点中增加了指向下一个叶子节点的指针. 范围查询只需找出首元素.

> [!example] 叶节点(非叶子节点) 作用? 
> 存储指向叶子节点的指针, 不存储数据, 一个叶节点可存储更多叶子几点, 降低高度
> 最底层的叫叶子节点，这些节点会*存储实际的数据*，例如聚簇索引中就直接存储对应的行数据，非聚簇索引中则存储指向主键/聚簇索引的字段值. 同时每个叶子节点之间都有一根*单向指针*指向下一个节点，从而使得最下面的一排叶子节点之间又形成了一个单向链表结构，方便范围取值

> [!abstract] 为何需要冗余节点?
> 节点有大小限制, 节点冗余后, 可存储的更多的索引键, 意味着树的高度将会更小, 因此磁盘IO次数更少.

> [!example] 如何计算千万级表索引高度?
> 1. *InnoDB* 单个节点占用一页大小为16KB. `{sql}SHOW GLOBAL STATUS LIKE "Innodb_page_size";` 
> 2. 指针大小, 64位用不上那么大, 压缩为6Byte. 
> 
> 假设索引字段为int, 占4字节. 单个索引信息: 6+4=10B;
> - 单个节点存储索引信息: $16K/10 ≈ 1638$ 个
>
> 假设每行数据大小1KB
> 因此, 高度为2的树可存储: $1638* 16 =26208$ 条
> 高度为3: $1638* 1638* 16 = 42'928'704$ ;
> 但这也只是索引字段为int, 行数据大小为1KB的大概

不过 __B+Tree__ 中的每个索引页中，还会存储页头（页号、指针、伪记录等）、页目录、页尾等信息，大概一共占用 __128Bytes__ 左右，因此想要真正的计算出来接近实际情况的索引树高，还需要把这点考虑在内

##### MySQL索引底层的真正结构
- `MySQL`在设计索引结构时，对于原始的`B+Tree`又一次做了改造，叶子节点之间除开一根单向的指针之外，又多新增了一根指针，指向前面一个叶子节点
- 也就是`MySQL`索引底层的结构，实际是`B+Tree`的变种，叶子节点之间是互存指针的
- 所有叶子节点是一个双向链表结构

##### 前缀索引提升索引性能
- 前缀索引限定索引大小, 节点可存储更多索引信息, 高度更小

#### InnoDB 与 MyISAM 存储索引
- 由于`MyISAM`引擎的非聚簇索引，关联的是行数据的指针，而`InnoDB`引擎关联的是聚簇索引的索引键，所以`InnoDB`的非聚簇索引在查询时需要*回表*，再查一次聚簇索引才能得到数据
- `MyISAM`每个非聚簇索引都能直接获取到行数据的地址，可以直接根据指针获取数据，从整体而言，`MyISAM`检索数据的效率会比`InnoDB`快上不少
- InnoDB查找到叶子节点后, 若为范围中的一个, 会在节点内进行二分查找
