# 为什么用sqlite, 为什么用TCP做断点续传, 不用HTTP的断点续传?
使用sqlite目的是可靠地、结构化地、持久化地管理任务. 同时HTTP 的 Range/断点续传只是「传输协议层面」的一环，客户端仍需在「应用层」有一套持久化、事务化、可查询的任务管理

1. 存储状态更丰富
    - HTTP Range 只能指定 byte‐range，客户端仍需记录每个任务的：  
        • 总大小、已完成偏移、分片列表、重试次数、校验信息、过期凭证等。
    - 用 SQLite 就能用表结构一条一条地保存、查询、更新这些字段。
2. 断点续传不限于下载: HTTP 的 Range 主要针对 GET 下载；断点上传需要自己设计分片接口、状态机、鉴权续签、合并回调……
3. 客户端崩溃／重启后能无缝恢复
4. 后续扩展方便: 比如做全局限速、断点合并、清理历史、统计报表……在 SQL 里一条语句就能搞定。

# C10K问题, 怎么处理?
- concurrent 10000 connection

1. 操作系统层面  
   - 提高文件描述符上限（ulimit、fs.file-max）  
   - 调优 TCP 参数（somaxconn、tcp_max_syn_backlog、SO_REUSEPORT 等）  

2. 非阻塞 I/O + 高效事件通知  
   - Linux 用 epoll，BSD/Mac 用 kqueue，Windows 用 IOCP  
   - 边沿触发（ET）或水平触发（LT）配合非阻塞 socket  

3. 事件驱动或异步并发模型  
   - 单线程 Reactor（Nginx、Node.js）  
   - 多进程/多线程 + Reactor（Nginx worker、Netty）  
   - 协程（Go goroutine、Python asyncio、Lua coroutines）  

4. 应用层和架构优化  
   - 连接复用（HTTP Keep-Alive/HTTP2 多路复用）  
   - 前端负载均衡（LVS/HAProxy/Nginx）+ 缓存与反向代理  
   - 水平扩展：多机集群、服务拆分、异步消息 MQ

# epoll的惊群效应. 怎么解决`EPOLLEXCLUSIVE` 
EPOLLEXCLUSIVE:
`EPOLLEXCLUSIVE` 是 Linux 4.5 引入的 `epoll` 标志，用来**避免多线程同时被唤醒造成的惊群效应**（thundering herd）

什么是*惊群效应*: 多个线程创建了多个epoll的实例, 监听同一个socket描述符时, 如果socket描述符可读事件到来, 那么**默认**这多个实例都会响应.

也就是<strong style="color:#e67e80">一次事件唤醒多个等待者</strong>.

而`EPOLLEXCLUSIVE`就是为了减少唤醒的等待者.
好处:*可以减少 CPU 浪费和锁争用*.

[Bryan Cantrill](https://en.wikipedia.org/wiki/Bryan_Cantrill "Bryan Cantrill") pointed out that `epoll` had mistakes that could have been avoided, had it learned from its predecessors: [input/output completion ports](https://en.wikipedia.org/wiki/Input/output_completion_port "Input/output completion port"), [event ports](https://en.wikipedia.org/w/index.php?title=Event_port&action=edit&redlink=1 "Event port (page does not exist)") (Solaris) and [kqueue](https://en.wikipedia.org/wiki/Kqueue "Kqueue")[^2]. However, a large part of his criticism was addressed by `epoll`'s `EPOLLONESHOT` and `EPOLLEXCLUSIVE` options. `EPOLLONESHOT` was added in version 2.6.2 of the Linux kernel mainline, released in February 2004. `EPOLLEXCLUSIVE` was added in version 4.5, released in March 2016[^1].

# 使用`epoll`都有哪些陷阱

##### Starvation

特别提出在ET模式下，因为需要一次性把数据读完，如果一次性通知的数据过大，有可能处理时间过长，导致同一线程其他的事件长时间等待。这个不仅仅是ET模式下，也不仅仅是epoll模型下才有的问题。对于网络接收模块，尽可能不要做额外工作，应该把数据接收出来，然后放到另一个分发线程，由分发线程分配到每一个对应的类中再做消息处理，减少接收网络消息使用的时间。不管有什么问题，在接收消息的时候占用过多时间，总归是不正确的做法，会产生各种无法预知的错误。

##### 多个线程同时触发读取事件

如果使用了同一个epoll，那么在一个线程收到读取事件，开始读取数据之前，又来了一个读取事件，也就是对方又发送了一条数据，这时可能会唤起另一个线程，处理这个读取事件。然而第一个线程还没有读，那么第一次触发读取事件的数据会与第二次触发读取事件的数据合并到一起，也就是任何一个线程调用read读取socket的信息，效果都是一样的。如果两个线程同时调用read，那么结果可能是未知的，所以为了避免这种歧义的操作，需要设置EPOLLONESHOT标识，这个标识的作用就是，每次触发事件，就会把这个socket从epoll的监听列表中删除，就算来了新的数据，也不会通知，这样我们就可以安心的处理数据，处理完成后，再把socket标识重置一下，放入到epoll的监听列表中，就可以等待下次数据到来的消息了。

##### 惊群 thundering herd

如果多个线程多个epoll，每个线程都在监听accept的消息，这时如果来了一个连接，所有的线程都会被唤醒去响应这次连接，但是只有一个线程才能成功响应，其余的线程都会报错。这个问题就是系统也不知道应该让那个epoll响应，所以就都唤醒了。可以设置SO_REUSEADDR，系统就可以自行判断，或是自己写一个全局的锁，每次竞争到锁的epoll才去响应
